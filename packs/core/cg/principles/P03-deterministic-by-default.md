# P3 Deterministic by default

Anything code can produce or check is produced or checked by code, and running it again gives the same result. The model judges; it does not compute, copy or transcribe.

**Why.** An output nobody can regenerate cannot be reviewed, defended or corrected. A tool is something a reviewer can rerun. A model's answer is not.

Terms used here are defined in the plugin glossary (`../GLOSSARY.md`): output, unit, worked example, tool, by code, by judgement.

## In production

### Plan

- Mark each step of the plan **by code** or **by judgement**.
- For each step by code, name the tool that will do it: a script, a pipeline target, a function, a check.

### Work: build the tool

When one operation applies to many units (countries, survey years, files, tables), the agent works in this order:

1. **Worked example.** The agent takes one unit through directly, step by step, and shows the human each step and the result. This is done by the agent, once, to learn what the tool must do. The human does none of it.
2. **Tool.** The agent writes the smallest script that performs those steps.
3. **Proof.** The agent runs the tool on that same unit and shows that it gives the result of the worked example.
4. **Run.** Only then does the tool run on the remaining units.

The worked example is a reference for testing the tool. The delivered output of every unit, including the first, comes from the tool.

A single obvious edit needs no tool. The bar is whether the step is trivial, not whether it repeats.

### Work: make the rerun identical

- Every table, figure, number in text, rendered page and index comes from one command that starts from the inputs. Nothing is typed, pasted or edited afterwards.
- Wherever code samples, bootstraps, simulates or splits, it sets a seed and records it.
- The environment is pinned: `renv.lock`, `uv.lock` or `poetry.lock`, the Stata version and ado versions.
- Paths are relative to the project. Timestamps stay out of outputs that are compared.
- Each operation is safe to run twice: it works from the state that exists, writes to a temporary path, then renames.

## Evidence it leaves

- The tool, in the diff. No tool in the diff means the principle was not applied.
- The one command that regenerates the outputs, recorded in the project's verification profile.
- A lockfile, and the seed where one is used.
- The repro record: two runs, same digests.

## Verifier: `determinism`

**At plan stage, inspect** the plan for steps that rely on the model or on manual effort where a tool could do the job.

**At review stage, inspect** the diff, the outputs and the work report.

Flag when:

- a table, figure or reported number is not regenerated by a tool from the inputs;
- a number appears in prose that no output file contains;
- a step needs a person to click, copy, paste or rename;
- code samples or simulates with no seed;
- the environment is not pinned;
- a path is specific to one user or machine;
- an output depends on row order, parallel scheduling or the clock;
- a run fetches from the network with no saved snapshot;
- an agent instruction asks the model for clerical work a command could do.

**Prove a flag** by naming the output and showing that no tool writes it, or by running the pipeline twice and showing the outputs differ. For each flag, propose the code that would replace the manual or model step.

**Leave alone:** interpretation, choice of method, and one or two obvious edits. Those are by judgement or trivial, and neither needs a tool.

## Deterministic checks

- `cg.py repro`: run the declared command twice and compare output digests.
- A lockfile exists for each language the project uses.
- A search of changed files for sampling and random calls with no seed nearby.
- A search of changed files for user-specific absolute paths.
