# ADR 0005: The artifact schema, approvals and the tier

Date: 2026-11-25. Status: proposed in task 2.1 (#224) as the working version. It waits for the review by Opus 5.5 and for the maintainer's acceptance. Before 2.0 it changes by amending this record. Amended the same day with the maintainer's decision on who answers for the data (under Tier). Reviewed by Opus 5.5 on 2026-11-26 (#224): its six fixes in code and the nine wording findings are written in below. Amended in task 2.2 (#225) the same day: an intent takes an approval, code checks what a brainstorm leaves open, and the replies that are not a yes are one list. Amended in task 2.3 (#226) the same day: a plan is built on a decided intent, code checks its checks, its slices and its data register, the record of an approval keeps the text, the artifact names its record, and an approved plan changes by an amendment. Amended in task 2.4 (#227) the same day: a work report takes the human's yes to a stop, it names its plan, and the three points this record left open for the work are closed in ADR 0006.

## Context

Artifacts carry the work between phases and between sessions. In version 1 nothing checked them: plans alone used thirty frontmatter keys, some with nested blocks, and a status was whatever the agent typed. A version 1 folder still has to be readable as it is. This repository's own has 668 artifacts.

The first gate (#223) also showed three things an agent gets wrong when they are left to its reading of a playbook: whether a record is complete, whether the human approved the plan as it now reads, and how risky a change is. Principle P3 puts each of them in code.

## Decision

### Schema 2

- **The marker is `schema: 2` in the frontmatter.** A file with no `schema` key is version 1. It is read as it is, in subfolders too, and it is never failed and never converted. Its type is its folder's, and its status is read through one table of version 1 statuses. A higher number than 2 is an error that asks for a newer core.
- **Frontmatter is flat.** One `key: value` line per key. A value is text or a one-line list such as `[a, b]`.
- **The schema is one table in `cg.py`, `ARTIFACTS`.** For each type it gives the folder, the statuses with what each means for status (waiting on the human, open, closed), and the headings the body must hold. The folders are version 1's, so old and new artifacts sit together. `templates/` holds one template per type, and a test holds each template to the schema.
- **Keys.** Every artifact has `type`, `schema`, `title`, `date` and `status`. A link to another artifact is a path from the project root under `intent`, `plan`, `work-report`, `review` or `supersedes`, and it must resolve. A work report on a plan names it under `plan`, written by `new work-report --plan` (task 2.4). `approval` is a link too: the record of the human's yes, written by `approve` (task 2.3). `size`, `decided-by` and `tags` are the other keys. Any other key is a warning.
- **A plan's contract carries IDs** (P1, and version 1 issue #66). Requirements are `R1`, `R2` and so on; checks are `C1`, `C2` and so on. Every requirement has a check that names it. Every check names a requirement that exists, a command, and the outcome that means failure.
- **A plan is built on a decided intent** (task 2.3). `cg.py new plan` takes `--intent`, makes no plan on an intent that is not decided on the human's yes to its text, and writes the path under `intent`. `approve` refuses a plan that names no intent, or one whose intent is not decided as it now reads. In a draft the same is a warning. After the approval it is not asked again: an intent that changes later shows under `waiting-on-human` by itself. Considered and set aside: a plan with no intent, which would need its own statement of a wrong result, its own facts and its own assumptions, so one understanding would live in two files; and a link the agent types, because nothing then looks at the intent before a plan is written on it.
- **Every check in a plan can fail, as far as code can tell** (task 2.3). A check's command and its "Fails when" cell are no placeholder (`nothing`), and the cell does not say that the check cannot fail (`CANNOT_FAIL`: a bare "never", "n/a" or "none", or a claim about the check such as "it cannot fail", "will never fail" or "always passes"; "never converges within 100 iterations" is an outcome). A plan that still marks something as open is not complete either (`open_marks`, from the review): a word in capitals such as `VALUE-PENDING` or `TBD`, `???`, or a request in angle brackets inside a cell is a warning in a draft and an error at `approve`. The playbook has the agent write such a request where a value waits on the human. A row with more cells than its table is named, so a `|` outside backticks cannot move the failing outcome out of view, and a requirement with no text is refused. Slices are `S1`, `S2` and so on. Each slice ends in a check that the Checks table holds, and a slice ends in every check: a check that no slice runs never fails. Each slice names the files it may touch, and says whether it is done by code, with the tool, or by judgement (P3). Whether a command can fail in fact, and whether an outcome is a matter of opinion, stay by judgement, for the `contract` verifier. Considered and set aside: a list of commands that always succeed, such as `true` or one that ends in `|| true`, because a check may be judged from its output, so the exit code proves nothing either way, and because lists of what is wrong keep missing cases (see Approvals); and a limit on the files of a slice, because a folder in the Files cell cannot be counted, and a warning that stays would fail a project's `--strict` run on a plan the human approved.
- **The data register is held to the recorded classifications** (task 2.3). Each dataset in the register has a rule recorded under `data` in `.cg-docs/config.json`, for the file or for a folder above it, the Classification cell gives that level, and no cell of the row is left unfilled. A folder in the register is held to every stricter rule recorded below it, as `tier` holds a folder that is read. Work with no dataset has one row that says "none". This is a warning in a draft and an error when `approve` is asked. It is not asked again after the approval, because a rule may change later and a completed plan cannot be amended. A level typed into the plan is a description, as "public" in a README is. Considered and set aside: the register as the place where a classification is declared, because `tier` would then have two sources.
- **An intent holds what grilling settled** (task 2.2). Beside goal, out of scope and a wrong result, its body has a Facts table, a Decisions table, an Assumptions section and the approaches considered (required since the review by Opus 5.5, whose finding W10 showed that the playbook asked for a section code did not hold). Every fact names its source. Decisions are `D1`, `D2` and so on, and each has a recommended answer and the human's answer; A cell that only stands for "not yet" means they have not answered: `open`, pending, TBD, a question mark and the like (`NOT_FILLED`), with or without marks of emphasis. The human's own words go in quotes when they start that way. The same holds for a fact's source and for a recommended answer. While the intent is a `draft`, a missing source or an open decision is a warning, because that is a draft's normal state. Once it is `decided`, and when `approve` is asked for, it is an error. Considered and set aside: decisions in a file of their own, because the human then confirms a text that does not hold what they decided.
- **Unfilled template text.** A line that is still the template's own request to fill a part in is a warning while the artifact has its first status, the one `new` writes. After that it is an error, so a work report cannot be `completed` with a part left unfilled. One request left anywhere in a line counts, and every cell a template leaves to fill holds a request, so a table row is unfilled until each of its cells is filled. A required section with nothing written under it is treated the same way: a warning in the first status, an error after it and when `approve` is asked. A table with its two header lines and no row counts as nothing.
- **`cg.py validate`** fails on errors. With `--strict`, for a project's CI, it fails on warnings too, so nothing half-written is merged.

### Approvals

- **One approval is one file**, `.cg-docs/approvals/<plan file name>.<start of the digest>.<number>.json`. It holds the plan's path, the digest, the human's reply word for word, the name and email from git's configuration, and the time. The number is the approval's place among the artifact's approvals (task 2.4), so a text that is approved a second time gets a record of its own and the earlier record stays. Until then the second record of a text got the time in its name, in a branch of its own in `approve`. Considered and set aside: the time in every name, which wrote over a record when one text was approved twice within a second (CI on `08925e26`).
- **The digest covers the plan's body, below the frontmatter.** Line ends and trailing spaces are left out, so a sync or an editor cannot void an approval. Considered and set aside: the whole file, because a status change would void the approval; and the Contract section alone, because the slices and the data register could then change with no new approval.
- **An approved plan is frozen.** Progress goes in the work report. A change to the plan is an amendment: the text changes, the human approves again, a second record is written, and the first one stays. Only the newest approval counts: a plan put back to a text that an amendment replaced needs a new yes.
- **Code moves the status from `draft` to `approved`**, and an intent's from `draft` to `decided`. A status typed into the file is not an approval: `validate` fails a plan whose status is `approved`, `in-progress` or `completed`, or an intent whose status is `decided`, with no record for its text, and `status` lists it under `waiting-on-human`.
- **`cg.py approve` records a reply only when it is a plain yes and nothing else** (the maintainer's two decisions of 2026-11-26, #225). The reply holds at least one of `YES` (yes, ok, okay, approved, confirmed, agreed, I approve, I confirm, I agree, go ahead, sí, si, de acuerdo, adelante), and every other word in it is of `FILLER` (please, thanks, the plan, as written and the like). A question mark refuses it too. Every hard stop that code records tells the human that a plain yes confirms. `approve` also refuses a plan or an intent that fails the schema or still holds template text, an intent with anything open, and an empty reply.
  - How the rule got here. Task 2.1 refused three replies by exact wording. Task 2.2 refused a list of openings and recorded the rest, so "I'd rather not" and a question were recorded. The first decision asked for a yes word; the review by Opus 5.5 then found 43 replies with a yes word that were not a yes ("Is this ok?", "OK, wait.", "Yes, drop D2"), fixed them with five more lists, and said that lists will keep missing cases. The second decision names what a yes is, and the lists of negations, conditions and corrections are gone.
  - What it costs. A clear yes that says more is refused and asked once more: "Yes, that is what I want.", "Sounds good. Yes.", "Yes, nothing to change." A refusal costs one question, and a wrong record sends data to the model or starts work on a text the human did not accept.
  - What the refusal says. `SAYS_NO` (an opening no) and `NOT_A_YES` (agreement without a decision, or the decision handed back) no longer decide anything. They choose what the refusal tells the agent to ask next. `grilling.md` names each reply and each word of `YES`, and a test holds the file to the code.
  - Still by judgement, for the `ownership` verifier: whether `--reply` holds what the human wrote.
- **The record keeps the text that was approved** (task 2.3), under `text`, as the digest sees it. P1 asks that the original stays readable after an amendment, and git cannot be relied on for that: a plan is committed only when the human asks. The playbook has the agent show an amendment against this text.
- **The artifact names its record** (task 2.3). `approve` writes `approval: <path of the record>` into the frontmatter, beside the status. The link must resolve, so a plan whose record is gone fails `validate` twice over. `validate` also holds the link to a record of this artifact, for the text as it now reads, whose kept text matches its digest: a link to another file, to the record of an earlier text or to an edited record fails. Considered and set aside: the name of the person in the frontmatter, because the record holds it, and artifacts are copied into evidence where a name does not belong.
- **An approved plan changes only by an amendment** (task 2.3). A plan that has an approval for another text is approved again only when it holds one more dated line under a heading `## Amendments` than the text in force had, such as `- 2026-11-26: what changes, and why`. Every earlier line stays as it was, and the new line holds text beside its date. The human then sees the change named in the text they approve. So a plan cannot be put back to an earlier text exactly: the way back is an amendment too. An intent has no amendments: it changes with a new yes. Considered and set aside: an amendment in a file of its own, the "delta" of `spec-driven-development`, because the checks would then live in two files and the work would have to merge them; and no rule in code, because an agent then rewrites an approved plan and asks for a yes without saying what changed.
- **`cg.py new plan` makes no plan beside an unfinished one** (task 2.3) unless the agent passes `--other-work`, which the playbook allows only after the human said that the new plan is other work and stands beside the first. `new` never writes over a file. Only schema 2 plans count: a folder of version 1 plans that nobody will finish would make every new plan ask.
- A plan and an intent take an approval, and so does the human's decision on data (under Tier). Since task 2.4 a work report takes one too: the human's yes to a stop of `tier`, recorded against the tier record it answers (ADR 0006). Sign-off (task 2.10) can use the same record.

### Tier

- **Two levels: `low` and `elevated`.** One yes makes the tier elevated, and elevated is a hard stop in quick work. A third level waits for an observed need.
- **Six facts are declared**, each yes or no, and `cg.py tier` refuses to answer until all six are: `number` (an estimate, a weight, a published output), `personal`, `irreversible` (a deletion), `interface` (a dependency, a schema), `choice` and `no-check`. The quick playbook defines each.
- **Two facts are computed.** `size`: the change touches more than five files. `data`: a data file the work reads is not cleared for this coding agent. A file is cleared when the rule recorded for it, or for the nearest folder above it, gives `Public`, or a level that `approved-tools` lets this coding agent read, ranked by `classification-levels`. A file with no rule is not cleared. A rule for the project root covers only paths inside the project. A folder given as read is held to every rule recorded below it.
- **The computed facts rest on what the agent passes**: the files in `--touches` and `--reads`, and the name in `--agent`. Nothing checks which coding agent is running, so the same file is cleared or not by the name given. This is a known limit.
- **The human answers for the data** (the maintainer's decision, 2026-11-25). Code records what the human declares and does not judge it: a file declared `Public` is cleared. The human may also decide that a coding agent reads a file that is not cleared. The agent warns them first, and `cg.py approve --reads <file or folder> --agent <name> --reply "..."` records the decision as one file, `.cg-docs/approvals/data.<digest>.json`: the place, the coding agent, the level the file had, the reply word for word, the name and email from git, and the time. From then on `tier` names the decision on its `data` line on every run and does not raise the tier for that file, and `status` lists it under `data-decisions`. The file still counts as not cleared.
- **In planned work the plan's approval is the recorded yes** (task 2.3). Every plan ends in a hard stop, whatever its tier, so no second record is needed. The plan playbook runs `tier` once for the whole plan: its `reasons` line is shown to the human at the hard stop, and its `data` line says which datasets this coding agent may read. A file that is not cleared is planned as closed, and a decision of the human to read it is recorded as in quick work, before the file is opened. Whether a coding agent may read a file is asked again when the work starts (task 2.4), because another coding agent may do the work. The lines of `tier` are not written into the plan by code. Since task 2.4 the lines of `tier` and the yes to a stop are records of the work report, in quick work and on a plan (ADR 0006).
- **A decision on data holds for one coding agent, one place and one level.** A folder covers what is under it, except a file with a stricter rule of its own; a decision for the project root covers nothing outside the project. Levels are compared without regard to case. When the file's level changes, the decision no longer covers it and the work stops for a new one. Considered and set aside: a key in `config.json`, because that file holds what the organization allows and a later `setup` run rewrites it; and a command of its own, because `approve` already checks the reply and the identity.

## Consequences

- A version 1 folder needs no migration step, and task 7.1 has no artifacts to convert.
- Later playbooks get their gates from code: the plan playbook (2.3) ends in `approve`, and work (2.4) can refuse to start on a plan that `validate` fails.
- `cg.py` is at 1,663 of its 2,500 lines, with ten commands of milestone 2 still to come. Tasks 2.2 and 2.3 added no command: an intent and a plan go through `new`, `validate` and `approve`. Task 2.3 added 113 lines to them.
- An agent can now read data its organization has not approved it for, when the human says so. The record names who decided, and the `governance` verifier leaves that decision to the human (P12, "Leave alone").
