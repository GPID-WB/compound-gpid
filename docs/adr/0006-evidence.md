# ADR 0006: Evidence, the guard, and the stops of the work

Date: 2026-11-26. Status: proposed in task 2.4 (#227) as the working version. It waits for the review by Opus 5.5 and for the maintainer's acceptance. Before 2.0 it changes by amending this record.

## Context

Until this task an agent proved its work by filling a work report: it typed the command, the exit code and the verdict of each check, copied the lines of `cg.py tier`, and wrote down that the human had said yes. `cg.py validate` could only see that no cell was left empty. Three things followed. A check could be run in another way than the plan wrote it, or not at all, and the report read the same. A work report was `completed` because its status said so. And the human's yes at an elevated tier was the agent's sentence about it.

The plan asks for more at the end of each slice (section 4.3): evidence exists for the slice's checks, no test was weakened or skipped, and the files touched match the slice. ADR 0005 left three points open for this task: what holds the work to an approved plan, whether code records the lines of `tier`, and whether code records the yes at an elevated tier in quick work.

One rule from the first gate (#223) governs every stop here: most people let their coding agent approve its own tool calls, so no stop may rely on an approval prompt.

## Decision

### Evidence

- **One run of a check is one record, written by code.** `cg.py evidence` runs the command, and writes one file under `.cg-docs/evidence/<name of the work report>/`, named `<number>-<time>-<label>.json`. Nothing is ever written over: the number is the record's place among the records of that work report, and it gives the order. Considered and set aside: one file that grows, because two people on two branches then change the same file; and the time alone in the name, which the approval records showed to collide within a second (ADR 0005, "Approvals").
- **A check ID runs the command the approved plan declares for it.** `cg.py evidence C1 --report <work report>` reads the plan the work report names, and runs what its Checks table holds for `C1`: the first text in backticks in the Command cell, or the whole cell when it has none. It runs through the shell, from the project root. It refuses when the work report names no plan, when the plan does not hold that ID, and when the plan is not approved as it now reads, so a check cannot be made easier by editing the plan. Considered and set aside: taking the command from the agent beside the ID, because the command is then the agent's and the ID only a label; and reading the exit code from what the agent reports, which is what the work report did before.
- **Anything else is ad hoc.** `cg.py evidence --run "<command>"` records any other command with `label: ad hoc`. An ad hoc record never stands for a check of the plan: `guard` and `validate` look for a declared record under the check's ID. Quick work has no plan, so each of its checks is ad hoc, and the label says so.
- **A record holds a digest and counts, never what the check printed** (P12). Its fields: the work report, the check ID and its label, for a declared check the plan and the digest of the plan's text, the command, the exit code, the verdict, the SHA-256 digest of what the check printed with its number of lines and of bytes, the commit, a digest of the state of the declared files, and the time. The command is cut at 300 characters and kept whole as a digest. A record names no person. What the check printed is shown to the agent, as it would be if the agent ran the command itself, and is not stored. Considered and set aside: storing the last lines of the output, because a check on a dataset prints rows when it fails; and hiding the output, because the agent would run the command a second time outside the record.
- **Code gives the verdict from the exit code, and the agent may only lower it.** Exit code 0 is `verified`, anything else is `not verified`. A plan may judge a check by what it prints, so `--verdict not-verified` and `--verdict inconclusive` let the agent record a failure that the exit code does not show. Nothing makes a failed run `verified`. The newest record of a check is the one that counts.
- **Evidence holds for the files as they were when the check ran.** Each record holds one digest over the declared files that differ from the last commit. `cg.py guard` compares it with the files as they now are, so a check that passed before the last edit does not count. Considered and set aside: the commit alone, because work is often not committed slice by slice; and a digest of every changed file, because checks write files of their own (a cache, a snapshot), and two checks of one slice would then never hold together.
- **A work report is completed on evidence** (version 1 issue #98). `cg.py validate` fails a work report whose status is `completed` when a check of its plan has no declared, verified record, when quick work has no verified record at all, when no risk was computed for it, or when a stop is not answered. A work report completed before this task has none of these records and fails until its status is set back.
- **The work report names its plan.** `cg.py new work-report --plan <plan>` writes the link, sets `size: standard`, and moves the plan from `approved` to `in-progress`. It refuses a plan that is not approved as it now reads, and a second work report while one for that plan is not finished. One plan has one work report at a time, so its evidence is in one place.

### The tier record and the stops

- **`cg.py tier --report` writes what it prints as a record of the work report.** The agent copies nothing. The record marks the start of quick work or of a slice: the facts as declared, the reasons, the files, the data lines without any name, and a digest of every file that had already changed, so that `guard` can tell this slice's changes from what was there before.
- **On a plan, the slice says which files it may touch.** `tier --slice S1` takes the files from the plan's Slices table: paths, folders or patterns, apart by commas or spaces. The agent does not pass them.
- **A stop is a reason that needs the human's yes before the work goes on.** In quick work every reason is a stop, as before. On an approved plan the plan's approval covers what the plan says, and the stops are the reasons of `ALWAYS_STOP`: for now `irreversible` alone. A plan that is not approved as it now reads covers nothing. Considered and set aside: `personal` in the list, because most survey data are personal data and every slice of most plans would then stop; and letting the plan's approval cover an action that cannot be undone when the plan names it, which the issue rules out ("irreversible actions always stop").
- **Code records the yes to a stop.** `cg.py approve <work report> --reply "..."` takes a plain yes and nothing else, by the rule of ADR 0005. It writes one record under `.cg-docs/approvals/`: the work report, the tier record it answers and its digest, the reply word for word, the name and email from git, the time, and what the work report said under `## Risk` when the yes was given. It refuses while nothing is written there, so the short contract of quick work, or the action that cannot be undone, is in a file before the human answers. This closes the point ADR 0005 left open: in quick work the lines of `tier` and the yes at an elevated tier are records now. Considered and set aside: a digest of the whole work report, as a plan has, because the report goes on changing as the work does.
- **The yes holds for one tier record.** Run again with the same facts, `tier` writes a new record, and its stop is a new one. An action that cannot be undone therefore stops each time. The yes is held against the record's file and against what it holds: two records written within a second hold the same text, and a yes to the first must not cover the second (CI on `7162a8b7`).
- **No check is recorded past an open stop.** `evidence` refuses, `guard` fails, `validate` fails a completed work report, and `status` lists the work report under `waiting-on-human`. `evidence` also refuses while no risk was computed at all, so the step cannot be left out.
- **What code cannot do.** It cannot keep an agent from deleting a file or pushing a branch. The stop itself is the playbook's: a question in the reply, and then the turn ends. Code makes a skipped stop visible and keeps the work from being completed past it. Step X of the gate measures the stop with approval prompts off.

### The guard

- **`cg.py guard` fails when a change lowers the bar** (P4). It compares each changed file with the commit, new files included, and counts four things before and after: tests and assertions in a test file (fewer is a failure), skip marks in a test file, and marks that silence a checker in any file (more is a failure). A deleted test file fails too. The patterns are one table, `GUARD`, for R, Python, JavaScript and the shell. It prints the rule and the file, with line numbers for what was added, and never the line, which may hold a value. Exit code 2 means that it could not run, and is never read as clean. Considered and set aside: reading the diff hunk by hunk, as the reference this is adapted from does, because it takes more code and calls a moved line a removed one; and its three other rules (a lowered threshold, unfinished work, a new exception), which belong to a constraints file that this project does not have: here the plan is the contract, and `approve` holds it.
- **With `--report` it holds the change to what was declared** (P6, and the plan's section 4.3). A file that changed since the slice started and that the slice does not list fails, and so does a check of the slice with no verified evidence on the files as they now are. In quick work the files are those given to `tier`, and one verified check is asked for.
- **`guard` reports and records nothing.** A finding the human accepts, such as a test that goes with the code it tested, is written in the work report. Considered and set aside: a record of each run that `validate` would ask for, because a finding the human accepted would then keep the work open for good.

## Consequences

- Quick work has four more lines to run (`new` moves to its start, then `approve`, `evidence`, `guard`), and no table to fill with exit codes.
- The work playbook gets its gates from code: it starts on an approved plan, each slice starts with a tier record, and a slice is done when `guard` prints `guard: clean`.
- `cg.py` grew by 337 lines in this task, after the trims of 29 lines that the review of task 2.3 listed: `evidence`, `guard`, the tier record and the yes to a stop.
- The records under `.cg-docs/evidence/` are committed with the work. They hold file names and digests, and no data.

## Open

- Whether `personal` (credentials, access rights) joins `ALWAYS_STOP`, and whether a push to a branch that only the human reads is an action that cannot be undone. Both are the maintainer's.
- Still by judgement: whether the facts given to `tier` are true, whether a command given with `--run` is a real check, and whether `--reply` holds what the human wrote. The `verification` and `ownership` verifiers look at these.
- `guard` does not see an expected value or a tolerance that changed in a test that stays, a test file that was renamed is named as deleted, and Stata's `capture` is not in its table. Language packs may bring their own patterns later.
- A check runs through the shell of the machine: `cmd.exe` on Windows. A command written for another shell fails there, and the record shows it.
- `guard` looks at the newest tier record. A slice whose stop was never answered is not seen once the next slice has started, except that no check of it could be recorded.
- Without a commit after each slice, `guard` tells this slice's changes from earlier ones by the digests in the tier record, not by the commit.
