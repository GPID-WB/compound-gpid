# ADR 0009: The determinism verifier: what code holds of P3, `cg.py repro`, and the first lens

Date: 2026-11-27. Status: proposed in task 2.6 (#229) as the working version. It waits for the maintainer's acceptance. Before 2.0 it changes by amending this record.

## Context

The issue asks that the verifier of P3 flags outputs not regenerated by a script, numbers typed into prose, manual steps, unseeded randomness, unpinned environments, user-specific paths and order dependence; that each flag proposes the code that would replace it; and that it catches its planted violations. It also asks for `cg.py repro`, which runs the declared pipeline twice and compares the digests of the outputs.

A verifier is a model that reads its principle file and its lens (ADR 0008), and CI cannot start a model. P3 asks that whatever code can check is checked by code. mattpocock's `retro` draws the same line for a reviewer: a mechanical violation gets a check, and a rule in prose is kept for a judgement no check could make. So each flag was split in two: the part a rule can find, which code finds, with a test; and the part that needs judgement, which the lens names.

Three things were given. Setup writes a verification profile, `.cg-docs/verification.md`, with a Run command and an outputs map (P4). Task 2.4 records each run of a check as a file under the evidence of the work report. Task 2.5 lists `lenses/<verifier>.md` as the third file of a kickoff, so a lens needs no change to code.

## Decision

### What code holds, and what stays by judgement

| Flag | What code finds (a rule of `repro`) | What stays by judgement |
|---|---|---|
| An output no script regenerates | no Run command; an output of the map that neither run wrote, or one run only; one missing after the runs; one that differs from what was on file; files the runs made that the map does not name; a run that failed | whether a path of the map is an output or code; an output the map leaves out |
| A number typed into prose | a decimal, a number with thousands separators or a percentage in the prose of an R Markdown or Quarto file, outside code and headings | whether it is a result an output holds; a number in any other document |
| A manual step | nothing | a step that copies, pastes, types, renames, clicks or exports, in the plan, a README, a report or the work report |
| Unseeded randomness | a draw in R, Python or Stata with no seed at or above it in its file; a seed with no value seeds nothing, and a seed given to one call seeds its own line; an output the two runs wrote differently | a seed set in a file that runs first; a seed set inside a function |
| An unpinned environment | R or Python code with no lockfile at the root; a do-file with no `version` command | an R package, which pins nothing in `renv.lock` |
| A user-specific path | a path under a home folder, `/Users/`, `/home/`, `C:\Users\` or `~/`, in code | a drive or a server path that one machine has |
| Order dependence | an output the two runs wrote differently; a listing of files in Python with no `sorted()`; a call to the clock | whether the order or the time reaches an output that is compared |

A network address in code is found too, for the fetch with no saved copy that P3 lists. Each rule says whether it names a fault (sure) or a line to judge, in the lens. Code proposes a fix for every finding: each rule carries the code that would replace what it finds, in R, Python or Stata, and `repro` prints it beside the finding.

### `cg.py repro`

- **The pipeline and its outputs come from the verification profile.** The Run command is the one line of the block under `## Run` that is no comment; "not found", a request in angle brackets, and a block of more than one such line are no command (review: a comment was run in the command's place, and a block of two lines ran its first). The outputs are the paths in backticks under "Where it lives" in the outputs map: a file, a folder by the files in it, or a pattern. Considered and set aside: a command given on the command line, which lets the agent run anything and call it the pipeline; the plan's checks, which check outputs and do not make them; and a key in `.cg-docs/config.json`, which would be a second place for what the profile says.
- **It runs the command twice, in the project, through the shell, as `evidence` does.** The human runs it there, and its relative paths and its data are there. So it writes the outputs where they live, and the playbook says so. Since task 2.7 it first refuses while an output is not as the last commit holds it ("Changes"). Considered and set aside: running it in a copy outside the project, which copies data out of the place its rule names (P12), costs a copy of every input, and still reads and writes the real project when the code holds a path under a home folder; and a git worktree, which lacks the data git ignores and the change that no commit holds yet.
- **What it compares.** For each output, the time it was written and a digest, before the runs and after each. An output is `same`, `differs` (the two runs wrote different bytes), `changed` (both runs wrote the same bytes, and not those that were on file), `not-written`, `once` (one run wrote it, as a cache does, so the second run was no rerun) or `missing`. The record's verdict is `verified` when both runs ended with exit code 0 and every output they both wrote is the same; `not verified` when a run failed or an output differs; and `inconclusive` when there is no Run command or no output both runs wrote. Exit code 0 only on `verified` with no finding.
- **What it searches.** The files of the change since the work began, by their suffix: R, R Markdown, Quarto, Python, notebooks, Stata, the shell and YAML. It opens no file that a data rule names, and none of a megabyte or more. A comment line counts for nothing; in a report, what stands between fences is code, and the rest is prose without its headings. Lines in a row that one rule finds are one finding, with a range.
- **What it records.** One record of `"kind": "repro"` in the evidence of the work report, beside the records of task 2.4: the command, cut at 300 characters as a check's is, with its digest; the exit codes; the digests and the verdict of each output; each finding as its rule, where it shows and its fix; the files the runs made, by a digest of each name; the commit; and the state of the change. It never holds what the command printed, and it never shows it: the pipeline of the planted project prints a household, and nothing of it reaches the record or the screen. A finding names a file and a line and never what the line holds, which can be a value or a path with a person's name in it (P12). An output that a folder or a pattern of the map holds is kept by a digest of its name too, and shown by its name (review: a file named after a person reached the record). A verifier points at the record, and `cg.py conformance` takes it as proof for the work report it names, as it takes the record of a check (ADR 0008, amended).
- **Who runs it.** The work playbook, once every slice is done and before the verifiers, so each verdict is on the change as `repro` left it. Nothing is changed for its findings: the verifiers read them, and the human decides. The verifier never runs it: the runs write the outputs, and rule 7 of `verifier.md` lets a verifier leave nothing in the project but the record of a run. Quick work does not run it, since its text is as earlier gates passed it; nothing keeps an agent from running it there. Like `evidence`, it runs nothing while a stop of the work waits for the human.

### Where a check or `repro` may write (gate rerun 21)

In rerun 21, `R CMD check .` wrote a folder `..Rcheck` into the project, and `guard` named it a change outside the slice, which the agent could only undo or declare. A run that code records now keeps the files it made, those that git neither held nor ignored before it, by a digest of each name. `guard` names such a file `written`, with the run that made it, and still fails: the file is deleted, which a new run of the same check undoes, so it is not an action that cannot be undone. A file that existed and that a run changed is still `outside`. Considered and set aside: leaving such files out of `guard`, which would let them into a commit; and a temporary folder for every check, which changes the commands the human approved and has no equal in `cmd.exe`.

Two sentences follow from the same rerun. The plan playbook asks that a check runs on this machine as the project stands, needs no program or package the machine lacks, and writes nothing outside its slice. The work playbook asks why a check fails before the change: one that fails for a missing program or package proves nothing, and the plan has to change. A check at the plan stage that each command can start was not built: planning runs no code, a look-up of the program would have caught neither case of rerun 21 (the package was not installed, and LaTeX was missing behind `R`), and `validate` would then pass a plan on one machine and fail it on another.

### The lens, and the shape the next lenses copy

`packs/core/cg/lenses/determinism.md`, 55 of its 60 lines. Its frontmatter names the verifier, the principle and the sources. Its sections: what code found and where its record is; what to flag at the plan stage, where no code has run; a table of the flags, each with code's rules, marked sure or to judge, what the verifier judges, the code its fix proposes and a priority; how a flag is proved and the fix written; and what to leave alone. A lens adds to the "Verifier" section of its principle and takes nothing from it. A test holds the lens to every rule code writes, to a fix in every row, and to the frontmatter.

### The planted cases

`evals/planted/<verifier>/` holds `project/`, a small analytical project with each violation planted in it, its verification profile, a draft plan with the violations of the plan stage, and `expected.json`, which gives each case, where it shows, and the rule of code that finds its part. Nothing in the project's files says where a violation is. `tests/core/test_determinism.py` holds code's part in CI: every case with a rule is found, each finding has its fix, and no row, value or name is shown or kept. `evals/planted/run_planted.py` gives the lens the same project through Claude Code, Codex or Kilo, from the kickoff alone, and judges the verdict block from the files. The build agent did not run it with an agent.

## Consequences

- `cg.py` went from 2,430 to 2,611 of its 4,000 lines: 164 for `repro` and its rules, 17 for the files a run made, in `evidence` and `guard`, and for the proof.
- The close of work on a plan runs the project twice. For a long pipeline that is the longest step of the work, and no limit is set on it, as none is on a check.
- A FLAG of `repro` blocks nothing. Its findings go to the human through the verifier.

## What task 2.15 adds

A folder of planted cases for each other verifier, with the unweighted headcount of the plan's milestone 2 gate for `domain-lenses`; one test over every folder, so that a rule that misses a case of any verifier fails CI; the runner's results kept as evidence, with the agents and the dates; and the routing evals and the pressure cases of the plan.

## Changes

- 2026-11-27, review of task 2.6: the rules no longer take a seed with no value, or one given to a single call, for a seed of every draw below it, and they find more forms of a draw in each language; the Run command is one line; a folder the runs make is no missing output, and the names under a folder of the map are kept as digests; four fixes were corrected (one seed above the first draw, the shell command for `targets`, `uv init --bare` before `uv add`, a rebuild for a cache); a record of a run is proof only for its own work report. The runner gives each planted case a finding of its own, and step W asks for a record of `repro` that this work report wrote after its last slice began.

- 2026-11-27, task 2.7 (#230), two points of the review. First, stop rule 1 of the work playbook applied to `repro`: writing over a file that no commit holds is an action that cannot be undone, and the review measured a typed output lost that way. Before its first run, `repro` names each output of the map that is not as the last commit holds it (changed since, new, or ignored by git), and refuses. It runs on such outputs only when the newest tier record of the work declares `irreversible=yes` and the human's yes to that stop is on record, and that yes covers one run: the next refuses again. The work playbook says to commit the outputs when the human asks for that, or to stop as rule 1 says. Considered and set aside: running in a copy outside the project (the reasons above); keeping the bytes of each output in the record (P12); and taking the digests of the last run of `repro` as safe, which leaves the first run at the close unguarded. Second, R17: a `requirements.txt` in which every package pins its version with `==`, and an `environment.yml` whose dependencies each carry a version, count as a lockfile. A range, a bare name, or a file of options alone such as `-r base.txt` is still `unpinned`.

## Open

- Whether an R package needs `renv.lock`. Code names its absence; the lens tells the verifier to leave a package alone.
- Whether `repro` keeps running in the project. Since task 2.7 it writes over an output that no commit holds only after the human's yes, so the close of the work stops for the human whenever an output is not committed as it now is.
- Whether the candidate rules (`typed-number`, `clock`, `network`, `unsorted`) stay in code or go to the lens alone.
- A check at the plan stage that each command can start.
- Whether quick work runs `repro`.
- From the review of task 2.6: whether `repro` refuses a Run command with a pipe, which hid a failure (exit 0 and `verified` on a script that ended with exit 3), as the plan's checks do in their text; a time limit, since a run that a host stops at its own limit goes on writing the outputs with no record; a finding for an output of the map that is outside the project, which is left out with none; and whether a record with an output `changed` or `missing` can be `verified`.
