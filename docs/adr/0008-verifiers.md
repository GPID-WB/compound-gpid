# ADR 0008: The verifier engine: dispatch, kickoffs and the conformance record

Date: 2026-11-27. Status: proposed in task 2.5 (#228) as the working version. Reviewed by Opus 5.5 on 2026-11-27 (#228): its nine fixes in code are written in below, each marked as from the review. It waits for the maintainer's acceptance. Before 2.0 it changes by amending this record.

## Context

The plan (section 4.2) asks that each principle has a verifier, that dispatch is computed and not remembered, that a verifier gets the work and the approved contract and never the author's explanation, that each flag has proof, and that sign-off is not offered until every applicable principle has a verdict. Until this task two playbooks held a self-review in the place of the verifiers: the agent that wrote a plan or did the work read the "Verifier" sections of a few principles and judged its own work. Which principles it read was a sentence in the playbook, and its verdicts were cells of a table that it filled in itself.

Three things were given. Each principle file already names its verifier and the stages it runs at, in its frontmatter, and already says what that verifier inspects, flags, proves and leaves alone. The pack contract (ADR 0003) lets a pack declare lenses, each tied to a principle and a trigger. And no stop or check may rely on what one coding agent can do that another cannot (ADR 0004): where an agent cannot start another one, the same checks run in its own conversation and are recorded as a self-review.

The verifiers themselves are later tasks (2.6 to 2.11), and so are the review playbook (2.9) and sign-off (2.10). This record is about the engine they run on.

## Decision

### Dispatch

- **Which verifiers run is read from the principle files, each time.** `cg.py verifiers <artifact> --stage <stage>` lists one verifier for each principle file whose `stages` line names the stage, under the name its `verifier` line gives. No list of verifiers is in code or in a playbook. A playbook says which stage it is at, and nothing more. Considered and set aside: a table of stages and verifiers in `cg.py`, which is a second copy of what the principle files say; and naming the verifiers in each playbook, which is what the self-review did and what the plan rules out.
- **A stage belongs to one type of artifact.** The plan stage looks at a plan, review and sign-off at a work report, compound at a solution. `STAGES` in `cg.py` holds these four pairs, and a test holds the principle files to them. A new stage is a change to code. A new verifier at a stage that exists is a line of text.
- **A verifier reads its principle file, and a lens when there is one.** The "Verifier" section of the principle file is the instruction. When `lenses/<verifier>.md` exists beside the principles, the kickoff lists it as the third file. So tasks 2.6 to 2.11 add a verifier's own text by adding that file, and this task adds no placeholder for them. Considered and set aside: one placeholder lens for each of the eleven verifiers now, which is eleven files that say nothing yet; and moving the "Verifier" sections out of the principle files, which the maintainer accepted as they are.
- **A lens of an installed pack is one more verifier.** For each pack that `cg.py packs` finds, each entry of `lenses` in its `pack.json` runs at the stages of the principle it serves, when its `when` fits the work. Its verifier is named `<pack>.<id>`, and it reads the principle file and the lens file. `when` is the file patterns as text, apart by commas or spaces, as a slice's Files cell is written; or an object with `files` and, optionally, `track` (ADR 0003, amended). The files of the work are computed: for a plan, the files its slices list; for a work report, the files that differ from the commit the work began on. A pack installed twice gives its lens once (review: it was dispatched twice under one name). The validator asks that a lens `id` is lowercase letters and digits in words joined by hyphens, used once in the pack, because the name becomes part of a line that `verifiers` prints to run (review; ADR 0003, "Changes"). Considered and set aside: reading only the packs the project lists in its configuration, because a lens is then lost when that list is behind; and asking the agent which files changed.
- **When code cannot tell, no lens is ruled out.** A `when` that code cannot read, a slice that lists a folder or a pattern, and a project where git cannot compare each make the lens run. A name in a slice that the project holds as a folder is a folder, `data.raw/` too (review: its dot made it a file, and it ruled a lens out). A track narrows a lens only once the artifact names one under `track`; no playbook writes that key yet (task 2.14).
- **The stage after the work is review, and until the review playbook exists the work playbook dispatches it.** Section 6 of `work.md` runs `verifiers --stage review`: nine verifiers today. The self-review it replaces looked at three principles. Considered and set aside: a stage of its own for the close of the work, with three verifiers, which would put a stage into three principle files that the plan's table does not have. This one is for the maintainer: see the handoff.

### The kickoff

- **A kickoff is fixed text with paths and IDs that code computes.** The text is `templates/kickoff.md`. Code fills in the folder of the core pack, the verifier, the principle, the stage, the files to read, the project root, and pointers: the artifact; for a work report the commit the work began on, the plan and the record of its approval, the folder of the evidence, and the line of `cg.py evidence --run` for a run that code records; for a plan the intent it is built on. Its first line is the one that sends every started agent to `worker.md`.
- **This is what code holds of "never the author's explanation".** `verifiers` takes no text to pass on: its arguments are an artifact, a stage and a project. It copies no line of an artifact's body. Of the frontmatter it uses two links, `intent` and `approval`, and only when code holds what each names: `intent` when it is the decided intent that code finds under that name, `approval` when it is a record under `.cg-docs/approvals/` of this plan for its text as it now reads. Otherwise the kickoff says that the plan names no intent the human decided, or that the record it names is not that yes. So the same work gives the same kickoff, whatever the agent wrote about it in the work report, in a commit message or in the conversation. A test rewrites the first two and compares the output. Until the review a link was passed on when it named any file, so a note of the author's, or a file outside the project, went to the verifier as the human's contract: on an approved plan too, because the frontmatter lies outside the digest of an approval. One thing of the agent's is in every kickoff: the name of the artifact's file, which `cg.py new` makes from a title, 60 characters at most. `verifiers` and `conformance` take an artifact only under such a name, `YYYY-MM-DD-<a slug of 60 characters at most>.md`, directly in the folder of its type, and refuse any other with exit code 2 (review: any name, at any length and in a subfolder too, went into every kickoff).
- **What stays by judgement, and where the text for it is.** The agent that starts a verifier could add words of its own to the kickoff: the guide says to give it as printed, with no word added. A verifier opens files, and some of them hold the author's account: the work report is itself what the `claims` verifier inspects. `verifier.md` tells every verifier that a work report, a commit message and a comment are claims to check and never a reason for a verdict, and to open the work report only for what its principle names. Code cannot see what an agent typed to another agent. The gate reads the transcripts.
- **`verifier.md` is to a verifier what `worker.md` is to any started agent.** It holds what every verifier does and the verdict block, which takes the place of the report that `worker.md` asks for. Where a principle file says how to prove a flag, the finding is still written as `verifier.md` says: a pointer and one sentence, with what a command printed left out (review, W3; the "Prove a flag" lines of P4, P5 and P10 now say the same). Considered and set aside: writing these rules into each kickoff, which makes nine long texts to pass on in place of nine short ones; and keeping the block in the principles index, where it stood with fields that code does not record.
- **Considered and set aside: a kickoff of one line that tells the verifier to ask code for its instructions.** The agent would have less to copy. A verifier would then need a shell before it can read its task, and the plan asks that `verifiers` prints the kickoff of each.

### The conformance record

- **One file for each artifact, to which code only ever adds a line.** `cg.py conformance` writes `.cg-docs/conformance/<folder of the artifact>/<name of the artifact>.jsonl`. One line is one verdict, as JSON. The file holds every verdict that was recorded, oldest first, and the newest verdict of a verifier at a stage is the one that counts. Nothing in it is read, changed and written back: as first built it was, and nine verdicts recorded at the same moment left one, which a coding agent that runs its lines at once would meet every time. A line is added with one write to a file opened for appending (`append_line`). On POSIX that is one step. On Windows an append moves to the end and then writes, which is two steps, so two writers of one instant could land at one place, and the later line covered the earlier one after its writer had looked (CI on Windows, review). There the writers take turns, through a lock on one byte far past the end of the file, which no reader touches and which goes when the file is closed. A line that cannot be read, or that is no verdict that code writes for this artifact with a kind of review, stays where it is and counts for nothing (review: typed lines with no kind of review, with an unknown verdict or for another artifact had filled `missing`). After each write code reads the record back and adds the line again when it is not there, three times at most. Then it refuses with exit code 1 and says that the verdict is not recorded, and `recorded:` is printed only after the line was read back (review: a write that failed was said to be recorded, or ended in a traceback). A plan and the work on it have a record each, and the listing for a work report shows both. Considered and set aside: one file for each verdict, as the evidence has, because the glossary says that the conformance record is a file; a lock around a file that is rewritten, which is more code and one more thing a sync client can hold (the lock on Windows is around one append, and leaves no file behind); and one record for a piece of work across its plan and its work reports, because a plan can have a second work report after a first one was dropped.
- **A verdict is recorded only for a verifier that code dispatches.** The name given to `--verifier` has to be in the list that `verifiers` computes for that artifact and stage, at that moment.
- **Proof is a pointer that code can open.** A finding is given as `<pointer>: <one sentence>`. The pointer is a file of the project with a line that the file holds, written `path:line`, or with a range whose two lines it holds, `path:12-14`; or the record of a run of this work under `.cg-docs/evidence/`: the record of a check, or since task 2.6 the record of `cg.py repro` (ADR 0009). Code opens it. Backticks, bold and quotes around the pointer, and a column after the line, are read past. A file that a data rule names, by itself or by a folder, is no proof (a rule for the project root names none), and neither is a record under `.cg-docs/evidence/` that is not a record of a run of this work report, with a line or without (review: a line of a Confidential data file, a record the agent typed, the run of other work and a tier record had passed as proof, and the forms a reviewer writes most often had been refused). A finding with no such pointer goes under `unverified` in the record, and a FLAG none of whose findings has one is recorded with the verdict `UNVERIFIED`. Line 1 of any other file of the project passes: whether the pointer shows what the sentence says is for the human to judge. Considered and set aside: taking the proof as text, a command and what it printed, because code cannot check a sentence and because what a command prints on a dataset can hold rows (P12); and asking that a proof is always a run, because much of what a plan-stage verifier finds is a line of the plan.
- **A verifier proves by a run through `cg.py evidence --run`.** The kickoff gives the line. The run leaves a record with the command, the exit code and a digest, labelled ad hoc, and the finding points at it. At the plan stage there is no work report and so no such line: a finding points at a line of a file, or is recorded as unverified.
- **The record states the kind of review, for each verdict.** `--review independent` or `--review self-review` is required, with no default. The listing gives it for each verdict and counts both kinds. Code cannot see who gave a verdict, so this is the agent's declaration, as the six facts of `cg.py tier` are. Considered and set aside: `self-review` as the default, which is the safe side but lets a record be written by an agent that never thought about which it was.
- **The agent that owns the work records the verdicts.** A verifier returns its block and writes nothing but the record of a run. Considered and set aside: having each verifier record its own verdict, which would keep the author's hand off the verdict. It needs a shell in every started agent, it gives two ways to the same record, and code still could not tell who ran the line. The guide says to record what the verifier returned and to soften nothing.
- **A record holds pointers and short sentences, and names no person** (P12). Each sentence and each note is cut at 300 characters. The record does not take the name that git gives, unlike an approval, which is the human's own act. Code cannot keep a value out of a sentence: rule 6 of `verifier.md` does.
- **A verdict is on the text it was given on.** For a plan and for a solution the record holds the digest of the body, and the listing marks a verdict that was given on an earlier text. It is still a verdict: the mark is for the human. A work report changes as it is filled in, so its verdicts carry the state of the change instead: a digest of each file that the work changed since it began, with `.cg-docs/` left out, so that filling in the report moves nothing. The listing marks a verdict given before the change last moved, as for a plan, and a file that a verifier leaves in the project shows up the same way (review: a verdict on a work report counted for a change it never saw). Considered and set aside: counting an earlier verdict as none, which makes every edit of a plan a full round of verifiers.
- **Sign-off is blocked by a missing verdict, and by nothing else here.** `cg.py conformance <work report>` lists the plan stage on its plan, then review and sign-off on the work report, and ends with exit code 1 while a verifier that code dispatches has given no verdict. What applies is computed again each time, so a new lens that fits the work is one more verdict to give. A FLAG, an UNVERIFIED and an INCONCLUSIVE are verdicts: the human sees them and decides (P2), which task 2.10 builds. `cg.py approve` and `cg.py validate` do not ask for verdicts.

### The playbooks

- **The plan and the work playbook run one line each**, `verifiers`, and follow what it prints: the kickoff of each verifier, the line that records its verdict with the paths filled in, and the line that lists the record. How a verifier is started and how a verdict is recorded is said once, in the guide: since the review also that verifiers may start at once, that a finding and a note go to the shell in single quotes, and that a verifier that returns no verdict block is started once more and then recorded as INCONCLUSIVE.
- **At the plan stage a finding may be fixed, in two rounds at most.** After the second round the plan is not changed for a finding: the finding stays in the record and the human decides at the hard stop. For a finding the agent leaves as it is, it says why at the hard stop, and a correction the human asks for there gets one round of every verifier, with no fix for its findings (review). At the close of the work nothing is changed for a finding: the human decides what is fixed. A verdict marked as given before the change last moved is asked for once more.
- **On a plan the work report has no "Self-review" table.** `cg.py new work-report --plan` leaves it out, because the conformance record holds the verdicts and says who gave each. Quick work keeps the table and its self-review of three principles, as it was.

## Consequences

- Tasks 2.6 to 2.11 add a verifier's text as `lenses/<verifier>.md`, 60 lines at most, and task 2.15 its planted-violation tests. Neither changes `cg.py`.
- The close of work on a plan now starts nine verifiers where it read three sections. Nobody has measured what that costs in a coding agent.
- The two commands, with what they share, were 266 lines of `cg.py` after this task, at 2,371 of its 4,000. The fixes of the review took it to 2,430.

## Open

- Whether quick work runs its three principles through a verifier in a fresh context. The plan (section 4.3) says "one combined verifier pass". It is a self-review in the agent's own conversation today.
- Whether a verdict on an earlier text of a plan blocks sign-off, and what a fix at review has checked again (tasks 2.9 and 2.10).
- Where the track of a piece of work is recorded (task 2.14).
- Whether a finding keeps its sentence in the record or only its pointer, with the sentence in the review artifact (task 2.9). The record has no limit on the number of findings: in the review 60 of them made one committed line of 20,773 characters.
- Whether code reads the verifier's returned block from a file (`conformance --block`), which would end the quoting through the shell and the retyping by the agent that did the work; whether a finding that points at a data file is refused, where it is now recorded as unverified; whether `governance` also runs at sign-off, for P12's AI-use statement; and whether `track` is read while only the author writes it. Each is the maintainer's, from the review.
