A. Before CR

The original CG approach

Before the research module, Compound GPID was already a structured operating model for responsible AI-assisted development. It emphasized explicit workflow stages, verification, reusable documentation, and institutional memory.

Pre-CR baseline
1. A fixed workflow loop

Users moved through a repeatable sequence: setup, brainstorm, plan, work, review, fix-triage, and compound. The goal was not “chat until something works,” but “follow a visible process with checkpoints.”

2. Verification before trust

CG was designed around tests, review routing, execution reports, and captured evidence. The system treated verification as a first-class output, not an optional cleanup step.

3. Knowledge compounding

Each solved problem could be turned into a reusable artifact in .cg-docs/, so hard-won lessons became part of the system instead of disappearing into one-off chat history.

What CG was especially good at It handled engineering and data-science workflow discipline well: planning, implementation, general code review, test coverage, roadmap integration, and cross-platform adapter generation.

Why CR was needed

The gap in the original model

The core CG workflow was strong, but economics and research tasks needed deeper domain support. Research work is not just “more code.” It has its own failure modes, vocabulary, validation surfaces, and review needs.

Problem statement
Research-specific correctness risks

Generic engineering review is not enough for identification logic, derivation-code consistency, specification searching, replication requirements, survey weights, or publication output standards.

Research needed first-class routing

Without dedicated prompts and agents, research tasks either fell through the generic CG path or relied on maintainers remembering to bolt on extra checks manually.

The CR module extends CG with a parallel research workflow: dedicated prompts, research review agents, domain-specific skills, routing logic, and research-aware integration with the v1.0 platform.

Contracts
Research-aware shared system behavior

Platform
Integrated with v1.0 infrastructure
  • CR agents assigned in the shared model catalog
  • CR prompts wired into Brain consultation and active-state handoff
  • Cross-agent generated targets now emit /cr-* commands, CR agents, and CR skills
Most important design move CR was not bolted on as “extra docs.” It was integrated into the same control surfaces that make CG reliable: routing contracts, model governance, generated adapters, tests, review reports, and reusable knowledge artifacts.
Migration results

What was actually implemented in the v1.0 migration

The migration did not just copy files. It re-integrated research functionality against the current platform and added validation around the fragile parts.

Delivered phases
Review routing integration

research mode was added to the shared review-routing contract, routed through /cg-review, and made explicitly selectable from /cg-work.

Model governance integration

CR review agents were added to the shared model catalog with GPT-5.4 assignments so research review behavior is governed, documented, and testable.

Brain and active-state integration

/cr-review and /cr-work now consult the Brain, while /cr-work participates in the active-state handoff used by resume flows.

Generated target integration

The generator now emits CR commands, agents, and skills into the native adapter trees, keeping Copilot, Claude, Codex, and OpenCode aligned.

Validation outcome The saved review and work-report trail show focused targeted validation, cross-file contract fixes, and generated-tree parity checks rather than a one-time migration dump.
Why this matters

What users and maintainers gain from CR

The CR module makes the system better in two ways: it gives researchers a more appropriate workflow, and it gives maintainers a cleaner contract for how research work should be reviewed and integrated.

Practical value
For researchers

They can invoke prompts and review paths that understand econometrics, identification, publication standards, and replication constraints instead of forcing those tasks through generic coding prompts.

For maintainers

Research review is now explicit, routable, and test-guarded. That reduces drift and makes CR behavior part of the platform rather than tribal knowledge.

For the repo

Research functionality is now represented in canonical source files, generated targets, shared contracts, the model catalog, and the knowledge system, which makes future extension easier.

C. Proposed next steps

How to mature CR from successful migration to stable operating capability

The technical migration is effectively complete. The remaining work is mostly close-out and maturity work: one pending charter approval step, plus follow-on documentation, validation, and adoption improvements.

Recommended roadmap
1. Close the workflow loop Close the last Phase 7 governance step and align roadmap messaging
  • Resolve the pending charter Current Focus approval step
  • Update roadmap artifacts so CR shows up as a maintained capability, not just migrated content
  • Make the final state visible to resume and release flows
2. Harden test execution Make research integration easier to validate locally
  • Standardize the PowerShell/Pester runtime path on macOS
  • Install or document missing Python test dependencies like pytest for generator tests
  • Add one or two higher-level end-to-end CR journey tests
3. Tighten documentation Make CR discoverable to new users
  • Add a concise CR overview to the public docs navigation
  • Document when to use /cg-work versus /cr-work
  • Explain the research review path in user-facing docs, not only prompt files
4. Expand research-aware defaults Reduce dependence on manual prompt selection
  • Improve automatic detection of research-typed tasks
  • Route more existing cg-* reviewers to research-aware checks when appropriate
  • Keep additive composition rules explicit whenever agent families differ
5. Use CR to compound research practice Turn domain mistakes into reusable safeguards
  • Capture more research-specific solutions in .cg-docs/solutions/
  • Promote repeat patterns into instructions or skills when they recur
  • Use review findings to sharpen the research integrity layer over time
6. Present CR as an operating model Move from migration narrative to adoption narrative
  • Package CR as a clear capability for economics research teams
  • Show example use cases: identification audit, replication package review, publication output review
  • Position CR as a specialized extension of CG, not a separate system
Bottom line The important next move is not “add more CR files.” It is to make CR easier to discover, easier to validate, and harder to misroute. That is what turns a successful migration into a durable operating capability.
