# Context Layer — Planning Prompt for `/cg-plan`

## What we're building

Restructure the context layer of compound-gpid so that consumer projects get
a slim, project-specific `copilot-instructions.md`, a freeform
`compound-gpid.context.md` for project knowledge that grows over time, and
multi-folder workspace awareness.

## Strategy reference

`.cg-docs/strategy/2026-04-16-context-layer-restructuring.md` — the full
strategy session with decisions and rationale.

## Key design decisions (from strategy session)

1. **Slim approach**: `copilot-instructions.md` stays short (~40 lines). Critical
   facts inline. Deep context loads on demand via Step 0. Trade-off accepted:
   ad-hoc chat may not read context.md automatically, but structured `/cg-*`
   prompts always do.
2. **Charter stays read-only for enrichment**: `compound-gpid.md` keeps its
   structured format and change-control protocol. Growing knowledge goes to
   `compound-gpid.context.md`, NOT the charter. Only `Current Focus` and
   `last-reviewed` are updated by the system.
3. **Single ownership model for context.md**: No separate "user section" vs
   "AI section." One file, topic-based sections (Domain Rules, Data Sources,
   etc.). User edits freely. `/cg-compound` proposes additions into the
   appropriate topic section — user must approve. Git history tracks who wrote
   what.
4. **context.md is committed to git**: It's institutional knowledge shared with
   the team, not user-local config. NOT gitignored.
5. **Loading model**: `copilot-instructions.md` auto-injected by VS Code (every
   interaction). Charter + context.md loaded by Step 0 (every `/cg-*` prompt).

## Roadmap features to implement (milestone: `context-layer`)

1. **`slim-copilot-instructions`** — Slim project-specific
   `copilot-instructions.md` generated by `cg-link` and `/cg-setup`
2. **`project-context-file`** — `compound-gpid.context.md` file and Step 0
   integration in all `/cg-*` prompts
3. **`cg-compound-context-enrichment`** — `/cg-compound` proposes
   `context.md` additions after completed tasks
4. **`multi-folder-workspace-awareness`** — Multi-folder workspace section in
   `copilot-instructions.md` and prompt awareness
5. **`auto-update-current-focus-on-milestone-completion`** — Auto-detect
   stale Current Focus when a milestone completes

## Current state (what exists today)

### `copilot-instructions.md` (~150 lines, identical for all projects)
- Copied from compound-gpid global install by `cg-link` (Step 4) and refreshed
  by `cg-update`
- Has a `<!-- compound-gpid:managed -->` marker — if present, cg-link/cg-update
  overwrite it. If user removes marker, file is user-owned and untouched.
- Content: Pester safety rules (36 lines, irrelevant to consumer projects),
  language preferences, project context section that says "read compound-gpid.md",
  workflow entry points table, coding standards, testing requirements,
  documentation standards, version control rules, review depth tiers, priority
  system, knowledge compounding.
- Problem: too long, too generic, not project-specific. Wastes premium context
  window real estate.

### `compound-gpid.md` (project charter)
- Created by `/cg-setup`. Structured: Objective, Key Deliverables, Constraints,
  Current Focus. Change-controlled (archiving, `last-reviewed`).
- Read in Step 0 of every `/cg-*` prompt.

### `compound-gpid.local.md` (user config, gitignored)
- Key-value: language, project-type, review-depth, r-syntax.
- Read in Step 0 of every `/cg-*` prompt.

### Step 0 pattern (identical in every prompt)
```
### Step 0: Get Bearings
1. Read `compound-gpid.md` for project context.
2. Read `compound-gpid.local.md` for user config.
3. If charter missing, warn user.
```
Prompts are self-contained — each repeats Step 0 verbatim by design.

### `/cg-compound` (solution capture)
- Creates `.cg-docs/solutions/<category>/YYYY-MM-DD-<desc>.md`
- Does NOT currently modify any context files
- May suggest updating `copilot-instructions.md` if a pattern should become
  project-wide

### `cg-link` (scripts/link.ps1)
- Creates junctions for prompts/, skills/, agents/, instructions/
- Copies copilot-instructions.md with managed marker
- Updates .gitignore

### `cg-update` (scripts/update.ps1)
- Refreshes copilot-instructions.md if marker present
- Respects user ownership if marker absent

## Target state (what we want)

### 1. Slim `copilot-instructions.md` (~40 lines, project-specific)

**Template structure** (generated, not copied):
```markdown
<!-- compound-gpid:managed -->
# Project Instructions

This project uses [Compound GPID](https://github.com/GPID-WB/compound-gpid),
a structured AI-assisted workflow plugin. Prompts: `.github/prompts/`,
skills: `.github/skills/`.

## Project Identity
- **Name**: <from compound-gpid.md frontmatter or setup question>
- **Type**: <from compound-gpid.local.md>
- **Languages**: <from compound-gpid.local.md, with R dialect if applicable>
- **Review depth**: <from compound-gpid.local.md>

## Essential Rules
- Read `compound-gpid.md` for the project charter (objective, constraints, focus).
- Read `compound-gpid.context.md` for project-specific context and workspace notes.
- Check `compound-gpid.local.md` for per-user preferences (language, dialect).
- <2-3 key constraints from the charter, e.g., statistical correctness,
  never commit data, conventional commits>

## Workspace
- **Principal folder**: this one (<project-name>) — compound-gpid is active here.
- <other folders if configured during setup>
```

**Generation changes**:
- `cg-link` (link.ps1): Instead of copying the global copilot-instructions.md,
  generate from template using values from `compound-gpid.md` (project-name) and
  `compound-gpid.local.md` (language, project-type, review-depth, r-syntax). If
  these files don't exist yet, use placeholder values — `/cg-setup` will
  regenerate. Keep the managed marker for cg-update to refresh.
- `cg-update` (update.ps1): When refreshing copilot-instructions.md, regenerate
  from template (not copy). Must read project-level config to fill values.
- `/cg-setup`: After creating charter and local config, regenerate
  copilot-instructions.md with real values. In Mode B (returning projects),
  also offer to regenerate if the file is still the old generic format.
- The GLOBAL `copilot-instructions.md` in compound-gpid's own repo stays as-is
  (it's the compound-gpid project's own instructions, not a template for
  consumers). Add a TEMPLATE file (e.g., `.github/copilot-instructions.template.md`)
  that the generation logic reads.

**What moves OUT of copilot-instructions.md**:
- Pester safety rules → stay in compound-gpid's own copy only (irrelevant to
  consumer projects)
- R skill routing → already in `.github/instructions/r.instructions.md`
- Coding standards boilerplate → already available via skills
- Workflow entry points table → prompts are discoverable in `.github/prompts/`
- Review depth tiers → loaded by `/cg-review` when needed
- Priority system → loaded by `/cg-review` and `/cg-fix-triage` when needed
- Knowledge compounding → loaded by `/cg-compound` when needed

### 2. `compound-gpid.context.md` (new file, project root)

**Created by**: `/cg-setup` (Mode A: scaffold with suggested sections;
Mode B/scanner: pre-populated from project analysis)

**Template**:
```markdown
# Project Context

Additional context for Copilot and the Compound GPID plugin. Edit freely —
this file is committed to git and shared with the team.

## Data Sources
<!-- Where does data come from? File paths, databases, APIs -->

## Domain Rules
<!-- Project-specific rules that Copilot should always follow -->

## Work in Progress
<!-- Modules, features, or migrations currently underway -->

## Workspace Notes
<!-- Related folders, dependencies on other projects in the workspace -->
```

**Read by**: Step 0 in every `/cg-*` prompt. New line added:
```
3. Read `compound-gpid.context.md` for project-specific context.
   If it does not exist, skip — the user has not configured project context.
```

**Not gitignored** — this is institutional knowledge, committed to the repo.

### 3. `/cg-compound` context enrichment

After Step 4 (saving the solution file), add a new Step 5:

```
### Step 5: Context Enrichment
1. Re-read compound-gpid.context.md.
2. Consider: did this task reveal a domain rule, data source convention,
   or project-specific fact that would help in future tasks?
3. If yes, propose a specific addition to the appropriate section:
   > "This task revealed that [X]. I'd add this to the [section] section
   > of compound-gpid.context.md:
   > `[proposed text]`
   > Should I add it?"
4. If approved, insert into the correct section. Do not append at the end —
   place it logically within the existing structure.
5. If compound-gpid.context.md does not exist, suggest creating it:
   > "Would you like me to create compound-gpid.context.md with this finding?"
```

### 4. Multi-folder workspace awareness

**In `/cg-setup`**: Add an optional question (Mode A and Mode B):
> "Are there other folders in your VS Code workspace related to this project?
> If so, list them with a brief description of what they contain."

Store answers in the `## Workspace Notes` section of `compound-gpid.context.md`
AND in the `## Workspace` section of the generated `copilot-instructions.md`.

**In prompts**: The existing Step 0 pattern handles this implicitly — if
`compound-gpid.context.md` contains workspace notes, they're loaded. No
special prompt changes needed beyond reading the context file.

### 5. Auto-update Current Focus on milestone completion

**In `/cg-work`**: After marking a feature as done in `roadmap.json`, check:
- Is this the last in-progress/unstarted feature in its milestone?
- If yes, mark the milestone as `done` AND warn:
  > "Milestone '<title>' is now complete! The charter's Current Focus may be
  > stale. Run `/cg-strategy` to update it, or I can suggest a new Current
  > Focus now."
- If the user wants an inline update, propose new text and update both
  `Current Focus` and `last-reviewed` (with archiving).

**In `/cg-resume`**: During Step 0, cross-check: if Current Focus mentions a
milestone that's marked `done` in `roadmap.json`, flag it:
> "Current Focus references '<milestone>' which is already done. Consider
> running `/cg-strategy` to update direction."

## Constraints

- The managed marker (`<!-- compound-gpid:managed -->`) pattern must be preserved
  for backward compatibility. Existing consumer projects with the old
  copilot-instructions.md should be seamlessly upgraded on next `cg-link` or
  `cg-update`.
- compound-gpid's OWN copilot-instructions.md is NOT the template — it must
  remain the compound-gpid project's own instructions. The template is a
  separate file.
- `compound-gpid.context.md` must NOT be gitignored. It's institutional
  knowledge.
- Step 0 duplication is intentional (per project conventions). Every prompt
  gets its own copy of the updated Step 0 — do not factor it out.
- Template generation must work even when compound-gpid.md and
  compound-gpid.local.md don't exist yet (use fallback/placeholder values).
