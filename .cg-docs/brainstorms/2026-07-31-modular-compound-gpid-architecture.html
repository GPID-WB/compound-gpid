01 / Context

Why a revamp is needed now

The research suite is no longer a small extension. It is large enough to expose architectural boundaries that naming conventions alone cannot enforce.

Compound GPID currently combines product infrastructure, reusable technical knowledge, and user-facing technical workflows under the cg-* namespace. The origin/feat/compound-research-v2 branch adds a substantial research suite under cr-*: 11 research agents, 5 research prompts, 14 research skills, 2 new instruction domains, and integrations with existing CG workflows and shared contracts.

Relative to main, the branch changes 305 files, including generated Claude Code, Codex, and OpenCode targets.

A May 2026 brainstorm had already chosen a single-repository module system with shared, engineering, and research tags. This session deliberately reopened that decision. The newer branch demonstrates that the research behavior is valuable, but it also exposes incomplete architectural boundaries.

The revamp's primary goal is maintainability: core maintainers must be able to improve a shared capability or one suite without silently breaking another. A modest learning curve is acceptable if the manual and help system make suite selection and composition clear.

02 / Requirements

What the architecture must protect

The redesign is not a license to replace everything. It must preserve stable workflows while making ownership, composition, and regression boundaries explicit.

Product and governance

  • Keep a single repository, a single installation path, and one product version and release train.
  • Optimize for core maintainers. A public third-party plugin API and marketplace are not required in this revamp.
  • Preserve stable user workflows, especially /cg-*, the compound lifecycle, .cg-docs/, and installation behavior.
  • Permit a versioned, automated migration of project configuration and internal manifests.
  • Treat the research branch as a behavioral specification: preserve validated research capabilities, task taxonomy, and research-integrity safeguards while refactoring ownership and orchestration.

User-facing suites

  • Keep explicit suite commands rather than relying on an opaque universal router.
  • Retain cg-* as the general technical suite and cr-* as the research and analytical suite.
  • Let a suite compose reusable capabilities automatically. Users should not need to know dependency names.
  • Support soft project preferences such as technical-only or technical-plus-research. Preferences shape setup, help, recommendations, and default guidance; every explicitly invoked installed command remains usable.
  • Make the CG-versus-CR choice understandable through concise help, examples, and task-oriented documentation.

Architecture and safety

  • Separate the product into three layers: a small platform kernel, reusable capability packs, and user-facing suites.
  • Give every canonical prompt, agent, skill, instruction, and shared contract exactly one declared owner.
  • Prevent direct suite-to-suite dependencies. Both CG and CR must consume reusable implementation knowledge through capability packs.
  • Keep .github/ as the canonical runtime source in the first revamp and continue generating committed native platform trees from it.
  • Make canonical asset discovery namespace-agnostic. Adding a registered suite or capability must not require another hard-coded prefix branch in the generator.
  • Validate ownership, dependency closure, acyclic dependencies, forbidden cross-suite references, generated-target parity, and compatibility in CI.
  • Treat context size as an architecture constraint. Inactive suites may be installed, but their domain instructions and skills must not be loaded into routine sessions by default.

Scope boundaries

  • Deliver the architecture foundation and migrate the technical and research suites in the first revamp.
  • Design for future writing, presentation, dashboard, and application suites, but do not implement them in this iteration.
  • Use one product version. Independence comes from boundaries and tests, not separate release calendars.
  • Use project module preferences as a guidance and context boundary, not as access control or physical asset filtering.
  • Preserve CR behavior while reorganizing its prompts, agents, and skills around the new ownership model.

04 / Alternatives

Three approaches considered

The options differ mainly in where boundaries live, how much of the current packaging system they replace, and how strongly they prevent hidden coupling.

Approach Boundary Migration risk Long-term isolation Verdict
1. Layered registry Validated ownership and dependency metadata over .github/ Large but incremental Strong, with CI enforcement Chosen
2. Physical packages Top-level source directories and generated runtime trees Very large Strongest filesystem clarity Defer
3. Broad shared bucket shared | engineering | research tags Medium Weak as suites multiply Migration waypoint only
01

Layered Registry Over the Canonical Tree

Effort: Large

Keep .github/ canonical and introduce a validated architecture registry for the kernel, capability packs, and suites.

The kernel owns product-level infrastructure. Capability packs own reusable implementation knowledge. Suites own user-facing intent and orchestration. Suite manifests declare required capabilities, and CI verifies every asset's owner and every dependency edge.

This is logical modularity rather than a physical source relocation. It strengthens the current canonical-to-native pipeline instead of replacing it.

+Pros
  • Enforces ownership and dependency boundaries without replacing the current canonical runtime and packaging model.
  • Lets shared improvements reach both suites through explicit capability packs.
  • Supports incremental migration and rollback.
  • Keeps one release compatibility matrix.
  • Provides most of the isolation value of physical packages at lower cost.
-Cons
  • Boundaries are logical rather than visible as top-level source directories.
  • The registry, dependency validator, and compatibility tests become load-bearing infrastructure.
  • Capability granularity and neutral internal naming require careful design.

Recommended and chosen. It provides enforceable isolation while preserving the recently hardened .github/ canonical-source model.

02

Physically Modular Source Packages

Effort: Very large

Move canonical content into source packages such as packages/kernel/, packages/capabilities/testing/, packages/suites/technical/, and packages/suites/research/.

Under this model, both .github/ and all native platform trees would be generated from the package source. Ownership is physically obvious, and directory structure reinforces dependency rules.

+Pros
  • Makes ownership and module contents immediately visible in the filesystem.
  • Gives future modules a clean package template.
  • Allows directory boundaries to reinforce dependency rules.
-Cons
  • Makes .github/ a second generated layer and replaces a recently hardened canonical-to-native packaging model.
  • Requires broad changes to paths, references, tests, adapters, install logic, and contributor workflows.
  • Greatly increases migration, rollback, and generated-drift risk.
  • Is disproportionate while only two suites need migration.

Not justified in the first revamp. Reconsider it later only if logical registry boundaries prove difficult to maintain.

03

Parallel Suites With a Broad Shared Bucket

Effort: Medium

Complete the branch's existing shared | engineering | research tagging model, keep parallel CG and CR commands, and let CR workflows reuse CG-owned agents and skills directly.

This is the closest option to the current research branch. It gets CR working fastest, but leaves ownership and dependency boundaries implicit precisely where future modules need them to become explicit.

+Pros
  • Closest to the current research branch.
  • Fastest route to shipping the research suite.
  • Requires the least immediate restructuring.
-Cons
  • Encourages a growing, weakly defined shared bucket.
  • Leaves CR coupled to technical-suite ownership.
  • Does not make dependency closure or ownership reliably enforceable.
  • Scales through conditionals as new suites appear.
  • Does not adequately prevent shared changes from breaking a suite.

Useful only as a migration waypoint. It is the simplest short-term merge strategy, not the maintainable final architecture.

The decision

Choose the layered registry.

Preserve .github/ as canonical. Add enforceable ownership and dependency boundaries. Let CG and CR share capabilities without depending on each other's workflows.

This approach best satisfies the maintainability goal. It preserves the stable /cg-* surface while allowing research workflows to use coding, testing, visualization, and reproducibility capabilities without making the research suite depend on the technical suite.

Approach 3 may be used only as a temporary migration state while assets are classified. Approach 2 remains a possible later evolution if the logical registry proves difficult to maintain, but physical relocation is not justified in the first revamp.

05 / Dependency rules

Coupling must point downward

The registry is valuable only if its rules are executable. Every runtime reference must be explainable through this graph.

  1. Kernel code and contracts do not depend on capability packs or suites.
  2. Capability packs may depend on the kernel and declared capability packs.
  3. Suites may depend on the kernel and declared capability packs.
  4. Suites do not depend on other suites.
  5. Every asset has one owner, and every runtime reference resolves through the declared dependency graph.
  6. Platform adapters and generated targets are projections of the same canonical registry, not separate module implementations.
Suites CG technical and CR research declare capabilities.
Capability packs Reusable expertise may compose other declared capabilities.
Kernel Stable product contracts and lifecycle infrastructure.
Forbidden: CG suite ↔ CR suite dependency
06 / Compatibility

Change the internals, preserve the workflow

The redesign gets room to evolve configuration and manifests, but not permission to casually break the product's established user-facing loop.

Compatibility position

Stable workflows, migratable configuration.

One repository, one install, one version, and one knowledge system remain the governing product model.

  • Existing /cg-* commands remain the technical suite's stable interface.
  • Existing .cg-docs/ artifacts and the compound lifecycle remain shared product infrastructure.
  • CR behavior is preserved while its direct dependencies on CG-owned behavior are replaced with capability-pack dependencies.
  • Existing shared cg-skill-* identifiers may require compatibility aliases if neutral capability identifiers are introduced. The exact naming and deprecation policy belongs in the implementation plan.
  • Project module configuration may move to a new schema, but migration must be automated, idempotent, and backward compatible for a defined transition period.

08 / Planning questions

Decisions still to make

The direction is settled. These implementation choices remain open and should be answered in the phased plan.

Where should the registry live, and should ownership be centralized, distributed in per-pack manifests, or represented by a validated combination?

What is the smallest useful capability-pack granularity without creating a dependency graph that is harder to maintain than the current shared layer?

Which currently cg-* skills are genuinely technical-suite assets, and which are neutral capabilities that need aliases or eventual renaming?

Which CR branch tests and artifacts form the minimum behavioral baseline for migration?

What measurable context budget should CG-only, CR-only, and mixed sessions satisfy?
