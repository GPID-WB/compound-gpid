# Compound GPID 2.0: principles that are enforced, one guide, a hub of packs

## 1. Context

Compound GPID exists so World Bank staff can use AI agents and still own and understand what gets built. The loop and the philosophy are sound; the delivery has become large, unstable and hard to use.

This revision answers your feedback on the first draft:

1. The principles behind the three reference repos are extracted and compared (section 3).
2. Principles are no longer statements. Each one has a verifier that is dispatched at a fixed point and a conformance record the human signs (section 4).
3. A specific adoption ledger says which skills, principles and workflows we take from each repo, where each lands, and how it is credited (section 5).
4. `research_evidence/`, `/cg` versus `/cr`, the multi-repository idea and the name are answered in sections 6 and 8.
5. Nothing of value in v1 is discarded. Content is re-homed into packs; only the packaging machinery is retired (section 7).

Earlier decisions that stand: clean break with a one-time migration; brain, roadmap + issues, HTML views, wiki, token audit and release are kept; outputs are generated by code. One earlier decision is revised by you: instead of one plugin that installs everything, users install a small core and add packs.

### Amendments after approval (2026-11-24)

- **Audience.** The plugin is built first for economists, researchers and data scientists, and for the people who build their R and Python packages, pipelines and Shiny dashboards. It is not aimed at application development. Rigor and robustness of the calculation come first. Consequences: the default track is `analysis`; examples in principles and playbooks are analytical; a practice from the three source repos is kept only where it holds for analytical work; application-only practices stay out of core.
- **Verification and validation.** P4 now names both. Verification: the work does what the contract says. Validation: the result is right, against something independent of our code. pstack uses "verify" for the first and "validate" only for input checks, so validation in our sense is our own addition. Terms are fixed in `GLOSSARY.md`.
- **Data governance is its own principle, P12 Governed data**: general rules only. Classify before reading, keep restricted and personal data inside approved tools, record lineage, attach an AI-use statement at sign-off. P10 keeps correctness. There are now twelve principles.
- **No host is the base (ADR 0004).** v1 was written for one host and adapted to the others. v2 is written in the open skill format that every host reads, and any host-specific piece is an optional adapter. The human picks the coding agent they prefer.
- **Host findings (ADR 0001).** The pointer block is written once in `AGENTS.md`, and `CLAUDE.md` imports it with `@AGENTS.md`. The import was tested live. Codex and Kilo ignore `disable-model-invocation`, so the guide is designed to be safe when the model starts it (task 1.3). Skills call their scripts by absolute path.
- **Documentation.** Task 7.5 (#257) audits every documentation surface and adds a drift check. Standing rule from M1: a change to what a human types or sees updates the documentation in the same change.
- **Glossary.** The plugin glossary is `skills/cg/GLOSSARY.md`; it ships with core and is the single place where the plugin's terms are defined. Each project keeps its own `GLOSSARY.md` for its subject words, in the same format. This is mattpocock's glossary mechanism, not an extra file.
- **Shared language is its own principle, P11**, with a `language` verifier and a code check (`tools/check_glossary.py`). P8 keeps decisions and limits. There are now eleven principles.
- **The P1 verifier is named `contract`**, not `spec`, to match the glossary. Tickets that say "Spec verifier" mean this one.
- **This plan predates the glossary** and uses some words the glossary now avoids ("by hand", "kernel", "orchestrator"). It is left as approved; the glossary governs new text.
- **Host tests.** The build session could not run the hosts itself; see `docs/adr/0001-host-matrix.md`.
- **research-evidence.** The repository `GPID-WB/research-evidence` now exists (empty). Task 3.4 moves `research_evidence/` into it.

## 3. What governs the three repos, and how they differ

Read from the primary files: `skills/using-agent-skills/SKILL.md` (addyosmani), `README.md`, `SCOPE.md`, `writing-for-agents/SKILL.md` (mattpocock), `skills/poteto-mode/SKILL.md` and its `principle-*` skills (pstack).

### 3.1 Their principles

**addyosmani/agent-skills** (26 skills, lifecycle Define to Ship)
- Skills are workflows, not suggestions: steps in order, each ending in verification.
- When in doubt, start with a spec.
- Six operating behaviors: surface assumptions; stop and name confusion; push back, sycophancy is a failure; enforce simplicity; scope discipline; verify, don't assume.
- Every skill names the rationalizations for skipping it and rebuts them.
- A project-wide Definition of Done beside per-task acceptance criteria.
- The skills themselves are tested (linter, routing evals).

**mattpocock/skills** (27 small skills)
- The human keeps control of the process: small composable tools, not a framework that owns it.
- Alignment before action: grill until nothing is silently assumed. Facts are the agent's job, decisions are the user's.
- Shared language: a glossary, checked against the code.
- Feedback loops: no red-capable check, no next phase; test at seams agreed with the human.
- Care about design: deep modules, fight entropy on a schedule.
- Record only what cannot be recovered: tiny gated ADRs, out-of-scope records.
- Mechanical rules become checks; only judgement calls stay as prose for the reviewer.
- Every skill is permanent maintenance surface: a change needs an observed failure.

**cursor pstack** (48 skills, one entry point, 24 named principles)
- "If you want to go fast, go deep first"; less code, higher quality.
- Core: smallest change, subtract before adding, name the data shape first, attack the premise, **Build the Lever** (build the tool that does or proves the work; "no script in the diff means you didn't apply it").
- Verification: **Prove It Works** on the real artifact, fix root causes, sequence work into verifiable units, test behavior, **Explain the Number**.
- Architecture: model the domain, idempotent operations, boundary discipline.
- Delegation: guard the context window; never block on the human for reversible work.
- Meta: **Encode Lessons in Structure** (a lint or check before more text).
- Accountability: every reply names the principle that shaped a decision; claims are labelled measured, inferred or guess.

### 3.2 How they differ

| Dimension | addyosmani | mattpocock | pstack |
|---|---|---|---|
| Who drives | a gated lifecycle | the human, picking small tools | the agent; the human audits afterwards |
| Planning | spec and plan are required artifacts | conversation first; spec and tickets when work spans sessions | none by default ("the best spec is code") |
| Human's role | approve at phase gates | interrogated on every real decision | interrupted only for irreversible actions |
| Verification | evidence checklist per skill, Definition of Done | red-green at agreed seams | real artifact, reproduced findings, independent verdict |
| Determinism | scripts preferred inside skills | mechanical rules become lint | strongest: build the lever, idempotency, lessons into structure |
| Memory | specs and ADRs | glossary, ADRs, out-of-scope | edits to skills and repo checks; no knowledge base |
| Size control | linter budgets, rejection ledger | hard scope policy, 7 to 140 line skills | 48 skills hidden behind one entry |
| How principles bind | sections inside each skill | wording and governance | separate principle files, cited in replies |

**None of the three checks conformance to its own principles with a dedicated reviewer.** pstack comes closest: it makes the agent cite principles, and it has one single-rule reviewer (a comment reviewer). That gap is where Compound GPID goes further.

### 3.3 My view on what to take

- **From addyosmani:** the gated lifecycle, the six operating behaviors, anti-rationalization sections, the Definition of Done, and testing skills as software. It matches your audience best because approval is explicit.
- **From mattpocock:** the division "facts are the agent's job, decisions are the user's", the grilling interview, the glossary, gated decision records, and the scope policy. It is the best model of real shared understanding.
- **From pstack:** Build the Lever, Prove It Works, Explain the Number, Encode Lessons in Structure, verifiable units, labelled claims, and principles as separate files with a "when it applies" trigger. It is the best model of rigor and of determinism.
- **Not taken:** pstack's "never block on the human" and its no-planning default. We keep one narrow part: do not ask the human for anything you can look up or run. Also not taken: addyosmani's breadth of web skills, and mattpocock's reliance on one long conversation as the only handoff.

## 4. Our principles, and how each one is enforced

### 4.1 The ten principles

They merge the seven in `docs/philosophy.md` with the three repos and your determinism requirement. The seven design rules of the first draft map onto them (skills only and one front door become architecture decisions in section 6).

### 4.2 The enforcement mechanism

Each principle is one file in `skills/cg/principles/` with five fixed parts:

1. **Statement and why.**
2. **In production:** what the working agent must do at each stage. These lines are pulled into the playbooks and into `worker.md`, which every subagent reads first.
3. **Evidence it leaves:** the file or record that proves the principle was applied. Following pstack's rule, applying a principle produces something a reviewer can inspect.
4. **Verifier:** the instructions for a reviewer agent that checks one principle only: what to inspect, how to prove a flag, the output format.
5. **Deterministic checks:** the `cg.py` commands that check what code can check.

Dispatch is computed, not remembered. `cg.py verifiers --stage <stage>` prints exactly which verifiers run and the kickoff text for each. The guide starts each one as a fresh-context subagent that receives the artifact and the approved contract, never the author's explanation. Each verifier returns a verdict per principle: PASS, FLAG or NOT APPLICABLE, with proof for every flag (a command it ran, or file and line). A flag without proof is recorded as unverified. `cg.py conformance` writes the results to a conformance record, and sign-off is not offered until every applicable principle has a verdict. The human fixes each flag or accepts it with a written reason.

### 4.3 Who verifies what, and when

| Stage | Verifiers dispatched | Deterministic checks |
|---|---|---|
| Plan, before approval | Spec (P1), Determinism (P3: which steps should be scripts), Simplicity (P6), Domain lenses (P10) | plan has contract, checks declared, each check can fail |
| End of each work slice | none (kept cheap) | evidence exists for the slice's checks; no test weakened or skipped; files touched match the slice |
| Review, after work | Verification (P4), Determinism (P3), Adversary (P5), Simplicity and scope (P6), Spec fidelity (P1), Claims (P7), Domain lenses (P10) | rerun checks twice and compare digests; lockfile and seed checks; evidence ledger complete |
| Sign-off | Ownership (P2), Record (P8) | approvals on file, decision records linked, glossary terms consistent |
| Compound | Lesson (P9) | lesson links to verified evidence; duplicate and stale detection |

Your two examples, concretely:

- **Determinism verifier (P3).** At plan time it flags steps that rely on the model or on manual effort where a script could do the job. At review it inspects the diff and outputs for: tables, figures or numbers not regenerated by a script from raw inputs; numbers typed into prose; manual or GUI steps; unseeded randomness; unpinned environments (`renv.lock`, `uv.lock`, Stata and ado versions); user-specific paths; order dependence; network calls without a snapshot. For each flag it proposes the code that would replace it. `cg.py repro` supplies the hard evidence by running the declared pipeline twice and comparing output digests.
- **Verification verifier (P4).** It reruns every declared check itself, flags claims with no evidence, evidence from a proxy ("it compiles", "the file exists"), checks that cannot fail, and statistical outputs with no independent check (second software, reference value, or a prediction the user made beforehand). For any reported number it asks pstack's question: what else could this number be measuring?

Scaling by size: the quick lane runs the deterministic checks plus one combined verifier pass (P3, P4, P6). Standard work runs the table above. Deep and analysis work add domain lenses and bounded adversary rounds.

Two honest limits. Verifiers are model reviewers, so they reduce risk and do not guarantee anything; the deterministic checks are the stronger layer. And where a host has no subagent tool, the same lenses run in the main thread and the record says "self-review", not "independent".

Each verifier ships with planted-violation tests (a hand-typed table, an unseeded bootstrap, an unweighted headcount). A verifier that misses its planted violation fails CI. The same ten principles are applied to the plugin's own development.

## 6. Architecture

### 6.1 A hub and packs

Your idea of repositories that users draw on as needed is right, and it also solves the bloat: the core stays tiny and everything else is opt-in.

- **Hub:** this repository. It holds the pack index (`marketplace.json`), the installer, the docs site and the core pack.
- **Pack:** a folder of skills plus a small `pack.json`. A pack is installed on its own.
- **Tool:** a program with its own runtime, such as the evidence workbench. It lives in its own repository and a pack points to it.

| Pack | Contents (from v1) | Who installs it |
|---|---|---|
| `core` | `/cg`, playbooks, ten principles and verifiers, general lenses, `cg.py` | everyone |
| `lang-r` | the 8 R skills, R instructions | R users |
| `lang-stata` | 2 Stata skills | Stata users |
| `lang-python` | Python skill | Python users |
| `research` | `/cr`, research track, 15 `cr-skill-*`, 11 research lenses, `c-research/` layout | researchers |
| `writing-wb` | WB report writing, document rendering | report authors |
| `views` | HTML artifact views, dashboard, Markdown publishing | optional |
| `brain` | topic-level knowledge brain (basic index and search stay in core) | optional |
| `roadmap` | `roadmap.json`, strategy, GitHub issues sync | optional |
| `wiki`, `audit`, `release` | wiki, token and context audit, release notes | optional |
| `maintainer` | skill authoring rules, linter, pack validator | pack authors |
| tool: `research-evidence` | the evidence workbench application | researchers who need it |

**One repository or many?** My recommendation: packs as folders in this one repository now, with an index that can also point to other repositories. A pack moves to its own repository when it has a different owning team, a different release rhythm, or its own runtime. With one maintainer, many repositories today would bring back v1's version-skew problem across repositories instead of across folders. Because the index already accepts outside sources, moving a pack later is a one-line change, and other World Bank units can publish their own packs and register them in the hub. That is how this becomes a Bank-wide tool.

**How packs talk to the core.** One small contract, validated in CI:

- `pack.json` declares: name, version, minimum core version, skills, lenses (each tied to a principle and a trigger), tracks and playbooks, and any command alias.
- `cg.py packs` discovers installed packs; `cg.py verifiers` merges their lenses into the dispatch list.
- A pack's scripts live in its own folder and reach the core only through the `cg.py` command line. Nothing imports across folders.
- A project lists the packs it expects in `.cg-docs/config.json`; `status` names any that are missing and prints the one command that adds them.

Language and method skills are ported close to as-is, since they are opt-in. They are consolidated later only where routing evals show collisions or the description budget for a profile is exceeded.

### 6.2 `research_evidence/` explained

It is not a skill. It is a Python application: 41 source files, 7.7K lines, 26 test files, its own lockfile, Python 3.11 to 3.13, a local API and a browser review screen for ingesting sources and tracking claims against evidence. Skills are Markdown that any host reads with no setup; this needs an environment. Kept inside the plugin, every user's install and every release would carry and test it. In the hub model it becomes a tool in its own repository, and the `research` pack uses it when present. Nothing is lost.

### 6.3 `/cg` and `/cr`

Two doors, one engine.

- `/cg` is the guide in `core`. It handles everything, including research when it detects it.
- `/cr` comes with the `research` pack. It is a thin alias of about ten lines that enters the same guide with the research track declared.

Why keep `/cr`: the research lifecycle is different (scope, evidence, theory, method, execute, verify, communicate), and a wrong guess by the router would silently drop the research gates. Letting the researcher declare the track makes it a fact, not an inference. If `/cg` detects research and the pack is missing, it says so and prints the install command. Users remember at most two commands, and only researchers need the second.

### 6.4 The guide without an agent picker

1. **State on disk.** `cg.py status` reads `.cg-docs/` and git and prints the phase, what waits on the human, the next step and the playbook to read. The router holds no process content. This survives long sessions and context compaction.
2. **Routing** to a track (analysis by default, then build, bug, writing, understand) and a size (quick, standard, deep). Where the host has a todo tool, the steps are copied there.
3. **Stickiness** from a pointer block of ten lines or fewer in `AGENTS.md` / `CLAUDE.md` / `copilot-instructions.md`: if there is active work, run status first; for non-trivial work started without the guide, suggest `/cg`.
4. **Playbooks** open with an ownership statement and end with a `Reply:` contract.
5. **Two hard stops** for standard work: plan approval and sign-off with the conformance record. The quick lane has none unless `cg.py tier` reports elevated risk.

A Kilo agent mode can later be a thin wrapper around this skill.

### 6.5 Install

- `python install.py --packs core,lang-r,research`, or a profile: `economist`, `developer`, `everything`. It copies packs to `~/.agents/skills`, read by Copilot, Codex and Kilo.
- Claude Code installs the same packs from the hub's marketplace index.
- `install.py` refuses double installs, removes v1 links, and supports `--update`, `--add`, `--remove`.
- `setup` scans the project (R, Stata, Python files) and proposes the packs it needs.
- Nothing is linked into projects. Version skew is caught by a minimum-version field in project config.
- Marketplace install on World Bank machines is tested in task 0.1, here and on Windows.

### 6.6 Deterministic tooling

### Which model builds what

This is a judgement, not a measurement; M1 will show whether it holds.

| Work | Model | Why |
|---|---|---|
| Principle files (0.5), pack contract (0.6), all of M2 (playbooks, verifiers, kickoff texts), milestone gate reviews | Fable 5.2 | short files where wording decides agent behavior; few tokens, high leverage |
| M1 scaffolding, `install.py`, `cg.py` commands, CI, linter, M3 pack ports, M5 and M6 tooling, docs, issue creation | Opus 5.5 | well-specified, test-covered work; each ticket has acceptance checks |
| Review of any ticket | the model that did not build it | P5: the reviewer should not share the builder's blind spots |

Escalation rule: a ticket that fails its acceptance check twice on Opus moves to Fable. Because the plan, tickets and artifacts are on disk, any session on either model can pick up the next ticket.

## 12. Risks

- **Verifier cost and latency:** sized by tier; deterministic checks first; the pilot measures whether people wait for them.
- **Verifiers give false comfort:** every flag needs proof, every verifier has planted-violation tests, and the record states independent or self-review.
- **Pack contract grows:** six keys, validated in CI, changes need a decision record.
- **Double discovery returns:** one install location per host; `install.py` refuses doubles.
- **Windows launch friction:** tested in 0.1; launcher file written by setup.
- **Gates cause rubber-stamping:** two hard stops, domain-language checkpoints, and a rule to cut gates if pilots show bare approvals.
