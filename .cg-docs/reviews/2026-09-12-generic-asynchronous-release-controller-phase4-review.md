## Critical Findings

### P1.1: Generic Build Has a Circular PR Gate

**[P1.1]** [cg-architecture, cg-testing] `packages/cg-release/src/cg_release/github_checks.py:44-47`

**Issue:** `required_pr_checks()` requires every entry in `policy.required_checks` on the preparation PR head before `verify_merge()` can bind the release commit. The same list selects the release-mode workflows in `build_stage.py:42-55,108-121`. To use the generic build template, its `build` check must therefore be in that list. However, `templates/build.yml:5-13` has only `workflow_dispatch`, and its registration requires the request to be in `building` (`build_control.py:43`). The request cannot enter `building` until that very check has passed.

**Trigger:** Install and enable the reviewed generic template as instructed at `templates/build.yml:1-3`. Configure its `build` check together with the ordinary package CI check, as in `tests/test_build_tickets.py:19-25`. Merge the correctly reviewed preparation PR after ordinary CI succeeds. `prepare_stage.py:97-107` calls `required_pr_checks()` on the reviewed head. The generic build check is absent, so review binding fails with `E_CHECK_EVIDENCE`; no build ticket or dispatch can follow. Dispatching the template early cannot solve this because registration rejects the `awaiting-review` state. Even a later registered run is bound to the default controller SHA, not a PR-head check.

**Impact:** The supplied generic build route cannot complete Step 7 and reach Step 8. The single-workflow package-CI route can pass, which explains why the current integration tests are green.

**Evidence gap:** `test_build_tickets.py:32-37` supplies a completed `review-binding` directly. It tests ticket separation, not whether the two-workflow policy can reach that state. `test_phase4_worker.py` and `phase4_transport.py:71-100` exercise only the package-CI check path.

**Required correction:** Distinguish preparation-PR checks from post-merge registered release gates in the trusted policy and consumers, or provide another explicit stage-aware contract that avoids this cycle. Do not omit required release gates from final evidence. Add an end-to-end offline case with both actual template roles that starts before review binding and reaches verified build evidence without injecting a completed binding or inventing a PR run for the dispatch-only workflow.

### P1.2: Interrupted Build-Ticket Checkpoint Cannot Resume

**[P1.2]** [cg-adversarial, cg-architecture, cg-testing] `packages/cg-release/src/cg_release/build_stage.py:109-119`

**Issue:** A new build ticket gets a random dispatch nonce, then `checkpoint()` persists its intent and result in two journal transactions (`prepare_stage.py:20-27`). Only the digest is saved in the intent. If the process stops after the intent commit and before the result commit, the sealed ticket and its nonce are absent from `record.evidence`. The next worker creates a different nonce for `build-request-1`. Its digest conflicts with the retained intent, and the journal correctly rejects the transition. Neither the router nor the build stage has a reconciliation path for this condition.

**Executed proof:** Used the real in-memory `Journal`, the existing valid ticket fixture, and the real `build_step()`. Persisted `build-request-1` intent without its result to model process loss. The probe substituted only ticket acquisition, returning the valid fixture with the new nonce generated by `build_step()`. The next step returned `E_TRANSITION`; the original `build-request-1` intent remained. No remote call or implementation edit was used.

**Related interruption boundary:** `build_control.py:111-114` also separates the registration claim and result. A stop between them leaves an unresolved registration intent, while the next `claim()` rejects any existing intent at line 101. The coordinator's waiting guard at `build_stage.py:124-129` does not reconcile this claim. This is the same missing interrupted-checkpoint recovery problem, not a separate counted finding. The registration variant was established by code inspection, not an executed fault probe.

**Impact:** A normal runner cancellation or process loss can leave the admitted request and its version reservation permanently blocked on ordinary resume, even before a build dispatch occurs. This is a Phase 4 ticket/registration defect, not a request to implement Phase 5 publication recovery.

**Required correction:** Persist enough immutable ticket data to reproduce the same intent, or atomically record the controller-only ticket checkpoint. Reconcile interrupted registration against the exact recorded claim and actual run without granting a second source execution claim. Add worker restart tests at each boundary between intent and result, including ticket creation, replacement tickets, and registration. Keep journal append-only and do not clear or overwrite unresolved state blindly.

## Important Finding

### P2.1: ZIP Entry Count Does Not Bound Parser Allocation

**[P2.1]** [cg-performance, cg-data-quality, cg-adversarial] `packages/cg-release/src/cg_release/artifacts.py:54-82`

**Issue:** The pre-parser limit trusts the entry count in the ZIP end-of-central-directory record. Python's `ZipFile` builds its entry objects by reading the central directory; a forged smaller end-record count does not limit that allocation. The later `len(members)` check rejects the archive only after those objects exist.

**Executed proof:** Created a two-file ZIP entirely in memory. Changed both end-record counts to 1 with `struct.pack_into('<HH', raw, end + 8, 1, 1)`, without changing the two central-directory entries. Called `verify_archive()` with `max_artifacts=1`, using a wrapper that recorded the number of entries allocated by the real `ZipFile`. Result: `E_ARTIFACT allocated_member_counts=[2]`. Thus the archive is eventually rejected, but the asserted pre-allocation bound is bypassed.

**Impact:** A malformed source-produced archive can allocate far more parser objects than the policy permits in the trusted verifier. The 64 MiB compressed transport limit still applies, but it is not the configured entry-count memory bound. No large-memory exhaustion or credential exposure was attempted or established; this is classified P2 for the unusual malformed-input case.

**Required correction:** Walk and validate central-directory headers with bounded offsets and an entry counter before constructing `ZipFile`, rejecting at the first excess entry and checking consistency with the end record. Retain byte and decompression limits. Add a forged-count regression; `tests/test_artifacts.py:106-127` tests only an honest count and therefore does not detect this bypass. Correct the pre-allocation claim in the execution report after the implementation is verified.
