# Use an ESL-led router for theory-first ML guidance in economics

## Problem

The ML skill had grown into a large monolith that mixed statistical-learning
foundations, high-dimensional econometrics, sample splitting, evaluation,
causal ML, survey and panel design, R/Python implementation, and review rules.
That made ordinary activation expensive and made it difficult to tell which
reference controlled a particular methodological decision. The redesign also
exposed high-risk defects: malformed mathematical notation, an unseeded
stochastic forest example, non-target-conditional split rules, ambiguous DML
nuisance notation, incomplete survey safeguards, and weak route tests.

## Root Cause

Content ownership and activation routing were coupled. A single skill file tried
to be both the conceptual reference and the review/implementation dispatcher,
while tests checked global vocabulary instead of the route associations that
users actually depend on.

## Solution

Use a small canonical `SKILL.md` as a router and keep detailed guidance in
focused references. The successful layout is:

1. Define the task before choosing a method: prediction, descriptive learning,
   variable selection, causal estimation, heterogeneous treatment effects, or a
   nuisance function.
2. Record the prediction target or estimand, target population, loss, information
   available at prediction time, and dependence structure.
3. Route only the smallest useful set of references. The implemented router
   has eight detailed references:
   - ESL foundations and bounded neural-network method selection;
   - high-dimensional and regularized methods;
   - splitting, resampling, leakage, and evaluation;
   - trees, ensembles, and interpretation;
   - econometric causal ML and DML;
   - survey, panel, and target-population safeguards;
   - R implementation with `tidymodels`;
   - Python implementation with `scikit-learn`.
4. Keep non-negotiable boundaries visible in the router: no causal claim from
   predictive fit or importance alone, no preprocessing leakage, no iid split
   when the target requires group or time separation, explicit stochastic
   seeds, and no claim that `sample_weight` or `case_weights` implements a
   complete complex-survey design.
5. Make the ML review agent target-aware. Establish whether the task targets
   new rows within known units, new units, future periods, a new wave, or a
   population. Then choose group, temporal, blocked group-time, or optional
   stratified resampling in that order.
6. Allow either an untouched final test set or nested cross-validation, and
   branch held-out metrics by task: regression, probability prediction, rare
   classification/ranking, hard classification, forecasting, or DML/causal ML.
7. Record candidate model, feature, transformation, split, metric, outcome,
   tuning space, number of trials, selection rule, seed, weights, and test-set
   use in an ML specification/search ledger. Treat manual fit loops and branch
   searches as specification searches too.
8. Apply stochasticity rules rather than blanket seed rules. Seed randomized
   estimators, shuffled splitters, randomized search, bootstrap, and randomized
   decompositions. Record deterministic splitter parameters and input ordering
   without adding unsupported randomness.
9. Keep implementation examples explicit. Declare the positive class and
   probability column for classification; calculate training-mean out-of-sample
   R2 explicitly rather than silently substituting `yardstick::rsq`; exclude
   identifiers through the active recipe; and state package boundaries for
   weights, clusters, and design-based uncertainty.
10. Regenerate all native target trees from the canonical `.github` sources and
    compare generated bytes, not only filenames. Run focused route/content
    tests in addition to the repository-wide parity checks.

Representative routing and validation commands are:

```text
python3 -m pytest scripts/tests/test_cr_ml_skill.py -q
python3 scripts/cg_generate_targets.py --all
python3 -m pytest scripts/tests -q
uv run --project research_evidence pytest research_evidence/tests -q
```

The focused contract should structurally parse route rows, test unknown and
negative route cases, check semantic safeguards, reject nonprinting control
characters in references, verify generated bytes against canonical files, and
confirm CI/release inclusion. Do not rely on a test that merely searches the
whole router for every keyword.

## Why It Works

The router separates *what to load* from *what the method means*. Users get the
ESL spine and the specific decision surface needed for the task, while senior
econometricians retain the assumptions, estimands, and inference boundaries
needed for defensible research. PhD students can follow the same path from
prediction target and loss to resampling and interpretation without beginning
with an undifferentiated implementation catalog.

Target-conditional review prevents two opposite errors: rejecting valid
within-unit prediction because panel data exist, and accepting ordinary iid
stratification when new-unit or future-period generalization is required.
Task-specific metrics prevent classification or DML work from being forced into
regression-only reporting. Structural route tests prevent a plausible-looking
but incorrect reference association from passing review.

## When to Use

Use this pattern when a technical or research skill has accumulated several
subdomains with different assumptions, packages, or failure modes, especially
when the skill is activated frequently and only a small part is relevant to a
single task. It is particularly useful for ML guidance that must serve both
methodologists and learners, or that spans prediction, causal inference, and
complex survey data.

## When NOT to Use

Do not treat the router as a complete research design. It does not establish
identification, validate an exclusion restriction, supply design-based survey
variance, replace a structural derivation, or make a prediction target
scientifically appropriate. Load the relevant identification, measurement,
structural, derivation, provenance, or survey guidance when those boundaries
are active.

Do not use random iid splitting for panel, grouped, temporal, or survey data
merely because a package offers it. Do not interpret feature importance or
regularized coefficients as causal effects. Do not treat one numeric seed as a
repair for leakage, invalid overlap, unsupported weights, or a wrong target
population. Specialized engines such as `ranger`, `DoubleML`, causal forests,
XGBoost, or LightGBM still require their own API and uncertainty checks.

Finally, the canonical source remains authoritative. Native mirrors become
stale after a source edit unless the generator is rerun, and new source files
must be explicitly included in version-control operations rather than assumed
to be captured by a modified-file-only commit.

## Prevention

- Keep the activated router below the repository's thin-router limit and route
  by named need rather than duplicating detailed content in the core.
- Give every reference one clear role and maintain an explicit route fixture.
- Test exact expected and forbidden references for representative and negative
  tasks, including review/leakage and neural-network selection.
- Use a cumulative per-file/per-review reference budget in methodology review.
- Keep seeds, split design, metrics, tuning choices, package versions, weights,
  and final test use in the specification ledger.
- Regenerate all native trees after canonical edits and run byte-level parity.
- Cite stable scholarly identifiers or official package documentation for
  methodological recommendations.
